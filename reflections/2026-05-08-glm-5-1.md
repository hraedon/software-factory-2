## On the project

The router/gate/process architecture is well-decomposed. Each module has a clear responsibility and the data flow (worker → gate → router → substrate) is easy to follow. The `_PHASE2_DISPATCH` table and `_ESCALATABLE_KINDS` set make routing policy explicit and auditable.

However, the testing story has a significant blind spot: InMemorySubstrate diverges from real Postgres in ways that silently weaken test coverage. The string-UUID issue (BC-035) means three escalatable diagnostic kinds have never actually been exercised by any test. The claim-attempt reset (BC-036) means the escalation path itself has never fired through normal pipeline flow. These aren't theoretical — I watched both manifest as wrong assertions during test development.

The breadcrumb system is working well as a knowledge-transfer mechanism. Being able to read the resolved breadcrumbs gave me immediate context on prior decisions.

## On the work done

The `_ESCALATABLE_KINDS` documentation was straightforward. The one-line comment now makes it clear which kinds are worker-retryable vs deterministic, which was the stated unblock for the next step.

The e2e escalation test was harder than expected. My first approach (`import conftest` to trigger `impl_import`) hit the string-UUID parity issue — the import check was silently skipped, and ruff's F401 (unused import) fired instead as `impl_lint`. I pivoted to use `import os` (unused import, reliably flagged by ruff) and updated assertions accordingly. The test still proves the escalation path works, just through `impl_lint` rather than `impl_import`. The fake-claim injection (`SimpleNamespace(attempt_number=3)`) is an honest compromise given BC-036.

The real-Postgres smoke test is deliberately minimal — interface_spec lifecycle only. I initially tried the full 3-stage pipeline but the test suite's `from interface import compute` can't resolve against `impl.py`, and fixing that cross-artifact import story felt out of scope for a smoke test.

The `test_pipeline_idempotency.py` reformat by ruff was incidental — it was already out of format before this session. I included it in the commit since `make check` requires format compliance.

## On what remains

- **BC-036 fix** (substrate-side): InMemorySubstrate needs to preserve attempt counts across transition claim releases. Until fixed, the e2e escalation test can only exercise the router path, not the full claim→gate→escalate cycle.
- **Wave 7** presumably starts after these cleanups land. The spec §9 phasing says single-role end-to-end next.
- **Real-Postgres 3-stage smoke**: Once BC-035 is fixed, the full pipeline can be tested against Postgres with correct gate evaluation. Currently blocked by the same cross-artifact import issue.

## Gaps to flag

- **BC-035: `gate_process.py:99,110,119`** — `sub.get_work_item(interface_ref)` passes a string to a UUID-typed parameter. InMemory returns None silently; real Postgres handles it. Three gate checks (import, mypy, pytest) are no-ops in every InMemory test.
- **BC-036: InMemorySubstrate._claims** — `transition()` pops the claim dict, losing attempt history. Next `acquire_claim` starts at 1. Escalation (`attempt_number >= threshold`) is unreachable in InMemory pipeline tests.
- **`test_pipeline_idempotency.py`** — reformatted by ruff this session but the underlying changes were from a prior wave. Worth verifying no semantic drift was introduced by the reformat (it was purely whitespace).
- **No `__init__.py` in `tests/`** — `tests/__init__.py` exists but the test helpers (`_helpers.py`, `_mock_channel.py`) aren't in a package structure that supports `pytest -k` filtering well. Minor ergonomics issue.
