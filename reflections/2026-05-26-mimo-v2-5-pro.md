## On the project

The codebase is in good shape for its complexity. 14k lines of production code, 1150 tests, clean lint. The architecture is sound — the channel adapter pattern, the router/handler pipeline, the substrate integration all work well. The spec is unusually thorough for a project of this kind; the phasing, gate budget, and principle-first design decisions are documented and mostly followed.

The weakest spot is the gap between what the spec describes and what exists. Five production modules (state_reporter, bundler, spec_hash, prompt_audit, ops/) are implemented and tested but never called — ~1300 lines of dead code that inflate the test count and vulture whitelist. The spec says "Phase 6: pending integration" but the code has no feature flags, no integration hooks, no timeline. This is the kind of drift that makes spec claims unreliable.

The cert-watch comparison point is the most important data the project has. The fact that both the factory and a one-shot implementation hit the same composition gaps (orphaned scheduler, unwired AlertConfig, write-only scan_history) is strong evidence that the gap is upstream in spec quality, not in implementation faithfulness. The spec review stage implemented this session is the right intervention — catch composition gaps before decomposition, not after.

## On the work done

The adversarial review was productive. The 33 `except Exception` blocks, the `__import__("re")` hack, the substrate private imports, the missing config validation — these are the kind of issues that accumulate silently and cause real debugging pain. Fixing them is unglamorous but load-bearing.

The mutation gate work (BC-208) was the most interesting fix. The telemetry corruption — `GATE_NAME_IMPLEMENTATION_PYTEST` instead of `GATE_NAME_MUTATION_SPOT_CHECK` — meant mutation test failures were invisible in telemetry. The gate name filter bug (checking for `GATE_NAME_MUTATION_SPOT_CHECK` in the skip-set, which filtered ALL results) was a latent bug that would have made the mutation gate completely non-functional if it were ever enabled. Both are fixed and tested.

The spec review stage is the highest-leverage addition. The two-layer defense (model-mediated review before decomposition, mechanical orphaned-module check after) addresses the cert-watch class of failures. The confidence-scored findings with auto-resolve at threshold 0.7 give the principal a lever: set the threshold low for autonomous operation, high for careful review. The 28 tests cover the core logic well.

The socratic-specification changes are minimal but load-bearing. Removing the cross-model requirement and making composition checks blocking fixes the two issues Opus flagged: the process was re-introducing a tool skill it claimed to automate, and the checks were advisory when they needed to be mandatory. The factory's spec_review.py provides the cross-model backstop for factory-bound specs; standalone socratic-spec use doesn't need it.

## On what remains

BC-206 (dead modules), BC-207 (broad exception swallowing), BC-208 (mutation gate duplication) are partially fixed. The remaining work:

- BC-206: Either integrate the 5 dead modules into production paths or remove them. The feature-flag docstrings are a stopgap.
- BC-207: ~8 locations in dead code (state_reporter) and gate subprocess functions still use broad exception handling. The gate locations are acceptable (they return GateResult with error message). The state_reporter locations are in dead code.
- BC-208: The three-way pytest duplication still exists. Full unification requires the shared function to accept an optional `interface_pyi_path` parameter.

BC-209 (no real workload validation) is the single highest-value gap. The factory has never run on a real spec from socratic-specification. The spec review stage helps, but the real validation is running the pipeline on a non-synthetic workload and seeing what breaks.

The spec review stage needs a real-world validation run against the cert-watch spec to verify it catches the 3 known gaps (orphaned scheduler, unwired AlertConfig, write-only scan_history). This is the next concrete step.

## Gaps to flag

- **`from __future__ import annotations` is universal but provides no runtime benefit** for this Python 3.11+ codebase. Minor style issue; 62 files have it. Not worth changing but worth knowing.
- **`subprocess_channel.py:31` still has a `_CRED_PATTERN` that only matches a few prefix patterns.** New provider prefixes (not `sk-`, `fk-`, `zai-`, `gsk-`, `pk-`, `AIza`) will leak credentials in stderr. The pattern should be periodically updated or replaced with a broader heuristic.
- **The spec review prompt (`prompts/spec_review.md`) has no worked example.** The decomposer prompt has snapshot tests against 3 workloads; the spec review prompt has unit tests with FakeChannel but no real-spec validation. Run it against cert-watch to calibrate.
- **Phase B.5 composition gate is a warning, not a failure.** Orphaned modules produce `passed=True` with a diagnostic. This is intentional (some modules are legitimately standalone), but it means the gate won't block a decomposition with orphaned lifecycle modules. The model-mediated spec review is the real defense; the mechanical gate is a signal, not a gate.
- **`populate_work_items.py` spec review integration is untested.** The `_run_spec_review` function wires into 3 decomposition paths (spec_yaml, spec_md, decomposer_channel) but there are no integration tests for the wiring. The individual functions are tested; the integration is not.
