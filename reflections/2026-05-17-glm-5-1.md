## On the work done

The BC-180 fix (field validation filter) is the load-bearing one. The root cause is architectural: `GateResult.custom_fields` is a bag of key-value pairs with no type discipline. When `evaluate_review()` puts `review_findings` in the bag, it's intended for the *upstream revision* (an implementation item), but `gate_process.py` blindly writes it to the *current* work item (a review item). The filter is defensive but correct — it queries the workflow schema at runtime and discards invalid fields with a warning.

The BC-181 fix (budget guardrail) is simpler and less controversial. It mirrors the runner's `claim_near_budget` pattern exactly. The one design decision I'm uncertain about: should items at `attempt_threshold` be force-transitioned to `cannot_proceed`, or just left in `gating`? I chose the soft stop (release claim, continue) because transitioning to `cannot_proceed` from the gate process would bypass the router's escalation logic. BC-182 tracks the harder version.

The two observations from Opus that were new to me:
1. Gate crash-loop detection gap (now BC-182) — I had not thought about this.
2. Import feedback false positives (now BC-183) — I had seen the `wrong_module_name` entries in the runner log but hadn't connected them to the exhaustion cycles.

The ABCMeta observation was one I had already diagnosed differently (it's a model capability issue, not a pipeline bug).
