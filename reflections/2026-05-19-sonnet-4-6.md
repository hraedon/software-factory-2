## On the project

sf2 is in good shape structurally after this session. The god-module problem (gate.py at 1415 lines, runner.py at 1175) is resolved — gate/ package, inner_gate.py, jury_orchestrator.py, phase_defaults.py are all clean separations with no logic changes, just reorganization. The codebase is now at a point where adding a new gate type or a new stage doesn't require editing a single massive file.

The spec reconciliation was overdue. The gap between "spec is authoritative" and "spec describes 11 stages when 7 exist" was active misinformation for any new agent or human reading it. That's fixed. The K2/Tier-B contradiction in the spec had been quietly wrong for 17+ golden runs.

What continues to feel fragile: the test coverage gap between `make check` and a full golden run. The synthetic e2e test closes part of this — it exercises the claim→invoke→gate→route→schedule seam without PostgreSQL or real models — but it covers only the interface_spec stage with inner_gate_retries=0. The integration and outcome_verification stages still have no deterministic mid-tier test. Any structural change to gate/integration.py or the scheduler's handoff logic can pass `make check` and only fail in a golden run 45 minutes later.

## On the work done

The parallel subagent dispatch worked well and badly in equal measure. Well: three independent refactors (gate split, config extraction, runner decomp) landed simultaneously and their diffs merged cleanly — the file overlap was at import lines, not logic, and ruff --fix handled the cleanup automatically. Badly: the agents wrote to the main working tree rather than their isolated worktrees, which means we briefly had a partially-refactored codebase in an unknown state while all three were running. The worktree isolation claim in the tool description is aspirational.

The memory-mcp build was the most satisfying work of the session. The design decision (pgvector DIY over mem0/mempalace/Graphiti) was correct for the reasons Opus articulated: the branch question was answerable from existing data, the trial of mcp-memory-service would have validated a concept already validated, and the pgvector pattern was already proven by the substrate event log MCP. The implementation was fast because we had the pattern.

The credential hygiene arc was embarrassing but instructive. Two filter-repo passes with a push between them is the wrong pattern — the second push after the first filter-repo introduced the new password into GitHub's object database exactly the moment we were trying to remove it. The rotate_dsn.py script (getpass, no shell history) is the right permanent fix. Future me: never ask the user to paste a secret into the conversation; write the rotation script first.

## On what remains

**Needed before a meaningful Phase 6 golden run:**
1. BC-195 (integration gate namespace isolation) — the network exfiltration risk is real, `unshare --net` is a one-afternoon fix, and it should happen before running the pipeline on any fixture with sensitive credentials in scope.
2. Second fixture domain — a CLI tool or simple web service with different module structure than cert-watch. The pipeline is implicitly tuned to cert-watch's shape; generalization can't be assessed without a second datapoint.
3. Smoke golden run harness — a `make smoke` target using a 5-item cert-watch slice with a cheap model to close the test gap between `make check` and a full golden run.

**Infrastructure now in place that should be used actively:**
- `substrate-eventlog` MCP: `list_golden_runs` + `golden_run_summary` at session start instead of reading artifact files. This replaces 10-15 minutes of orientation per session with a single tool call.
- `git-constellation` MCP: `repo_status` at session start catches substrate API changes between sessions before they cause runtime failures.
- `memory` MCP: the 5 imported memories are a skeleton. The memory system is only useful if it gets written to. First session that learns something worth keeping should `add_memory` rather than edit a markdown file.

## Gaps to flag

- `inner_gate_retries=0` in `test_synthetic_pipeline_e2e.py`: the test deliberately disables the pre-gate subprocess loop (mypy/ruff/pytest) to avoid infrastructure dependencies. This means a regression specifically in the retry loop won't be caught. The docstring is honest about this but worth noting — the test is a seam test, not a gate coverage test.

- RFC-037 is marked "in-flight" but only BC-194 (its lead worked example) is implemented. The broader tier declaration convention (every signal-emitting check must carry a `# tier: detect/enforce/retire` annotation) hasn't been applied across gate/, pre_gate.py, or behavioral_gate.py. It will drift without a CI check.

- `phase_defaults.py` imports `RoleConfig` and `StageHandoff` from `config.py` — this works, but the dependency direction (defaults → config for schema types) means config.py and phase_defaults.py are coupled. If `RoleConfig` ever grows fields that need defaults, the question of where defaults live becomes murkier. Not a crisis now; worth a comment in phase_defaults.py.

- The memory-mcp server loads the sentence-transformers model on first tool call (~2s), not at startup. This means the first `search_memory` or `add_memory` call in a session has a cold-start delay. For an MCP server that Claude Code may invoke at session start for orientation, this is noticeable. Moving model load to server initialization (before the stdin loop) would fix it but isn't done.

- No test for `memory-mcp` at all. The project has smoke-tested end-to-end manually but has no automated test suite. If the psycopg schema changes or the embedding model API changes, there's no signal.

- All 38 golden runs are cert-watch. The spec now correctly labels this as Phase 6 work, but the risk compounds with each structural refactor: the pipeline's implicit tuning to cert-watch's characteristics becomes harder to see, not easier, as the code matures around it.
