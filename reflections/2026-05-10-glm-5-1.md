## On the work done

The core fix was straightforward: add a `dependency_pyi_paths` parameter to each gate function that creates a temp directory, and copy those `.pyi` files as `.py` files into the temp dir. The `_copy_dependency_pyis` helper is 7 lines.

The trickier part was the plumbing — getting dependency_refs from the spec text all the way through to the gate functions:

1. `populate_work_items.py` parses `## Dependencies / interface_ref: name` from spec markdown
2. `dependency_refs` stored as a custom field on the work item (UUID list)
3. Scheduler propagates `dependency_refs` from source → downstream items
4. `gate_process.py` resolves each UUID to an artifact path, passes `dependency_pyi_paths` to gate functions

The two-phase creation in `populate_work_items.py` (create all items first, then resolve dependency names to UUIDs and update via claim/release) is a bit clunky — substrate doesn't have `update_work_item`. I used the `claim` transition with `custom_fields` to set `dependency_refs` post-creation. This works but changes the work item through `new → in_progress → new`, which is a minor concern for idempotency if re-run on existing items.

The biggest surprise was that InMemorySubstrate initializes `dependency_refs` to `None` (from the JSON schema default) rather than `[]`. This caused a `TypeError: 'NoneType' is not iterable` in `_resolve_dependency_refs()`. Fixed with `or []` pattern.

I'm confident in the core gate.py changes. The scheduler propagation is simple and correct. The populate_work_items.py dependency parsing is the part I'd want a second look at — the regex for parsing `interface_ref: name` from markdown could be fragile if spec formatting varies, but it matches the cert-watch-mini fixture format exactly.

## Gaps to flag

- `populate_work_items.py:165-192` — The two-phase claim/release cycle for updating `dependency_refs` post-creation is a workaround for substrate lacking `update_work_item`. If substrate adds that method, this should be simplified.
- `src/factory/gate.py` — Three gate functions (`_run_pytest_collect`, `_run_pytest`, `_run_mypy`) now all accept `dependency_pyi_paths` as an extra parameter. The parameter list is growing (artifact_path, interface_pyi_path, dependency_pyi_paths, python_executable). Consider a `GateContext` dataclass if more parameters are added.
- `src/factory/gate_process.py:113-121` — `_resolve_dependency_refs` iterates over the UUID list and calls `sub.get_work_item()` for each. For work items with many dependencies, this could be slow. Fine for Phase 2 (1-3 dependencies typically) but worth caching if Phase 3 adds larger dependency graphs.
- `workflows/phase1.yaml` and `phase2.yaml` both have `dependency_refs` custom fields now. If substrate ever adds schema validation that rejects unknown fields on work_item types that don't declare them, adding the field to all three types was necessary. If not, the field on `interface_spec` is the only one that truly needs it — but propagating through scheduler to test_suite/implementation is cleaner.
- No integration test exercises the full dependency_refs flow end-to-end (populate → scheduler handoff → gate resolution). The unit tests cover each layer independently, but a golden run is the true validation.
