## On the project

The migration plan was well-structured — the deltas between phases are genuinely additive (roles, work_item_types, link_types appended; transitions get `allowed_roles__append`), making composition a clean fit. The substrate `_deep_merge` with keyed lists and `__append` worked exactly as designed. The project is in a healthy state: the workflow YAMLs are now a proper inheritance chain rather than 5 nearly-identical copies.

One worry: `full_pipeline.yaml` was explicitly excluded from composition because it diverges structurally (different work_item_types with `feature`, different transitions, no `release`/`channel_fail`). Over time, if more divergent workflows appear, the composition approach could become a liability. But for now, with a strict linear chain, it's a clear win.

## On the work done

The main surprise was substrate's keyed-list merge placing child items before parent items, which makes content_hash differ from the monolithic originals. This is benign (same logical content, different list ordering) but wasn't anticipated in the migration plan, which assumed content_hash would match. I adapted by switching to semantic verification instead.

The second surprise was that both `InMemorySubstrate.register_workflow_file()` and `Substrate.register_workflow_file()` (real Postgres-backed) needed the `extends:` composition fix — not just the test double. The real substrate's `register_workflow_file` was also just `Path.read_text()`. This means any production code registering composed workflow files would have silently failed before this fix.

The migration script was initially too complex (computing deltas, writing files). I rewrote it as a simpler verify/restore/status tool since the actual YAML files were written by hand. This was the right call — the deltas are straightforward enough that programmatic generation added complexity without value.

Confidence level: high. The test suite (947 + 529) provides strong coverage. The semantic verification confirms all 5 phases produce identical WorkflowDefinitions. The `phase3.yaml` being just 4 lines is satisfying proof that the composition works.

## Gaps to flag

- **Substrate changes are uncommitted** — `/projects/substrate/src/substrate/__init__.py` and `/projects/substrate/src/substrate/_in_memory.py` have uncommitted changes. If substrate gets redeployed or the venv is refreshed, these changes would be lost. The `register_workflow_file` fix is load-bearing — without it, any code path that calls `register_workflow_file` on a composed YAML will fail with "states is required".

- **`register_workflow()` still doesn't support `extends:`** — The method that takes a raw YAML string can't resolve relative `extends:` paths because it doesn't know the file's location. All 5 call sites were migrated to `register_workflow_file()`, but any future code using `register_workflow(yaml_string)` with composed content will silently fail. A docstring warning or a clearer error message would help.

- **Content hash ordering** — Substrate's `_deep_merge` places child items before parent items in keyed lists. This is documented behavior but could confuse future agents comparing composed vs monolithic hashes. The migration script's `--verify` flag documents this, but it's worth noting in `workflows/MIGRATION_PLAN.md`.

- **`workflows/.pre_migration_backup/`** — Contains the original monolithic YAMLs. Should be removed after GR-032 validation. Currently in `.gitignore`.
