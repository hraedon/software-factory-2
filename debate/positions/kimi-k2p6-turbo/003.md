# Position on Debate 003 — Channel adapter deduplication

**Agree with GLM: composition over inheritance. Agree with DeepSeek: equivalency test before extraction. The extraction order matters more than the abstraction choice.**

## Why composition beats inheritance here

A `SubprocessChannel` base class makes subprocess invocation the canonical abstraction. But K2 (Phase 3) is HTTP, not subprocess. If the base doesn't fit K2, then it isn't a common abstraction — it's an adapter for 2-of-6 channels masquerading as one. GLM made this argument cleanly; I agree.

The right structure:
- `factory/channel/_subprocess.py` — subprocess helpers (timeout handling, raw_stdout capture, error formatting)
- `factory/channel/_artifacts.py` — artifact extraction (output_extraction.py already exists, keep it)
- `factory/channel/_contracts.py` — dataclass defining the Channel protocol + a `ChannelContract` validator

Each adapter imports what it needs. Claude and OpenCode import `_subprocess` and `_artifacts`. K2 imports `_artifacts` and writes its own HTTP client. No template methods, no risk of base-class accretion.

## Why the equivalency test must come first

DeepSeek's framing is correct: "write an equivalency test for both adapters before extracting" defines what "common" actually means. Without the test, the extraction is guesswork.

The test:
```python
def test_channel_contract_consistency():
    """Both adapters must produce identical results for the same mock output."""
    # Given identical raw_stdout.txt + identical config
    # Both adapters produce: same artifact_name, same extracted content,
    # same error_message shapes, same timeout behavior
```

This test becomes the **specification for extraction**. Extract only what the test requires to pass. If K2 later needs a different timeout model, the test is updated, then the helpers are updated.

## Why not just copy-paste for now

The debate says "do not add K2/GLM/DeepSeek/Gemini adapters on top of duplicated code." This is the right constraint. But the fix is not "extract everything now" — it's "define the contract, then extract what the contract requires."

**Concrete sequence:**
1. Write `test_channel_contract_consistency` against Claude + OpenCode (1 session).
2. Extract `_subprocess.py` from the test requirements (not from the current code).
3. Refactor both adapters to compose `_subprocess` and `_artifacts`.
4. Only then add K2 adapter. K2 starts with `_artifacts` and no `_subprocess`.
5. After K2 is stable, evaluate whether a second extraction round is needed.

## Risk the debate undersells

The `output_extraction.py` module (already extracted) is the right boundary. But it has no tests that define its contract. Add `test_artifact_extraction_consistency` that asserts: given the same raw stdout with an artifact block, both `claude_code_channel._extract_artifact_from_output` and `opencode_channel.extract_artifact_from_output` produce the same result. Without this test, the extraction is faith-based.

## What I'd push back on

Opus's "conservative base class" position and Gemini's "refactor before 3rd adapter" both imply the extraction is straightforward. It isn't — the two adapters have diverged in timeout models (Claude has `--max-turns 1`, OpenCode doesn't), error message formatting, and family derivation. The equivalency test will surface these differences. Account for 1.5 sessions, not 1.
