# Position on R2-002 — Bidirectional Spec Mutability

**Defer to Phase 5+. The concern is real but the proposed mechanism is premature for current pipeline constraints.**

## Why the concern is real

In real software development, implementers frequently discover that a spec is contradictory, underspecified, or relies on an impossible constraint (deprecated API, unavailable dependency, platform limitation). The debate correctly identifies that sf2's current architecture assumes a strict linear flow: `Spec → Implementer → Gates`. If the spec is impossible, the implementer is trapped.

v1 had a similar problem: agents would write code, discover a spec contradiction, and either (a) silently work around it (drift), or (b) fail repeatedly without a clear escalation path (burn budget).

## Why the proposed mechanism is premature

1. **Today's specs are principal-authored, not Socratic-authored.** The principal reviews the spec before pipeline start. If the spec is impossible, the principal is the right person to amend it — not the pipeline. The `propose_spec_amendment` transition would route back to the principal anyway.

2. **The current escalation path handles this case.** `cannot_proceed` with `cannot_proceed_seam` diagnostics already routes to the principal. The implementer can include `spec_ambiguity` in the diagnostics. The principal decides whether to amend the spec or accept the scope reduction.

3. **Formalizing spec amendment in the event log is valuable but not urgent.** The debate proposes tracking *why* the spec changed. This is a good audit requirement but not a Phase 2–4 requirement. The worklog already captures spec changes manually.

## When this becomes load-bearing

Phase 5+, when:
- The socratic-specification process produces specs without principal pre-review
- The pipeline runs for days without principal attention
- Spec amendments are frequent enough that manual worklog tracking is insufficient

At that point, a formal `propose_spec_amendment` transition with:
- `spec_invalid` reason classification
- Routing to orchestrator/interface_architect
- Versioned spec artifact (see socratic-specification debate/001-schema-versioning)
- Event-logged amendment history

...is the right architecture. Building it now is infrastructure without a consumer.

## What I'd do now instead

1. Document in `spec.md` §11 that spec amendment is out of scope for Phases 2–4.
2. Add `spec_ambiguity` to `DiagnosticKind` in `router.py`.
3. Route `spec_ambiguity` to `cannot_proceed` with principal notification (R2-005 sink).
4. Add a worklog convention: when principal amends a spec, prepend a new worklog entry with the delta.

## What I'd push back on

The debate's framing implies the implementer should negotiate amended specs. This is wrong for sf2's constraint set: the principal is the systems architect, the implementer is not. The implementer should surface ambiguity, not resolve it. The principal resolves it.

## Connection to socratic-specification debate/004

If the socratic-specification process adds a `spec_smell` check (socratic-spec debate/004), many impossibilities are caught at spec-time, not implementation-time. The need for bidirectional amendment diminishes as spec quality improves. Invest in upstream spec quality before downstream spec amendment machinery.
