# Position on Debate 004 — Pipeline checkpoints

**Defer until you actually feel the pain. Keep the MVP design as a spec sketch.**

The debate is well-reasoned and the proposed minimum (~100 lines of stage-level checkpointing) is genuinely small. But every persisted artifact is a maintenance liability: schema versioning, validation on resume, config-hash matching, recovery from partial writes, the `--retry-escalated` semantics interacting with router escalation rules. Once it exists, every change to scheduler / runner / config has to consider checkpoint compatibility.

Today's evidence:
- 30–50min runs are not painful enough to justify this. A crash midway costs ~$2 of model spend and 30 minutes; an engineer noticing and restarting costs less than the engineer noticing and reading checkpoint code.
- BC-003 (per-work-item resume from manifest) already covers the only failure mode that has actually happened: crash mid-attempt. The checkpoint system addresses a failure mode (crash mid-pipeline losing in-progress work-items) that hasn't actually happened yet.
- "Config changes between checkpoint and resume" is exactly the kind of corner case that produces 4 follow-up breadcrumbs. The fewer such corners, the better.

**When to revisit (concrete triggers):**

1. A Phase 3 sequential-fallback chain (Claude → GLM → K2) pushes a single GR past 2 hours.
2. A real mid-run crash actually loses meaningful work (count of in-flight items × replacement cost > 1 hour of engineering).
3. Phase 5's first real workload requires `--retry-failed=<wi>` for incremental triage.

Any one of those triggers fires → re-open this debate with empirical data attached, then build the MVP from the existing design.

**On the v1 BC-122 reference:** v1's heavy checkpoint machinery (test architecture preservation, surgical FR redo, budget tracking) is exactly the kind of accretion v2 should not replicate. The fact that v1 *needed* it indicates a deeper problem (failures at hour 4 of an 8-hour run) that sf2 has not yet demonstrated. Don't pre-build for v1's failure mode.

**Disagreement with the debate's blocking claim:** Debate 004 lists Phase 3 as blocked. I don't see it. Phase 3 adds channel adapters; channel adapter additions don't make individual runs longer or more crash-prone. The earliest plausible block is mid-Phase 5.
