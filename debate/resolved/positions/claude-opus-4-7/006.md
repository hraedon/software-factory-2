# Position on Debate 006 — Per-project venv isolation

**Accept the principle. Reject the abstraction. Ship a 50-line shim, not a `VenvManager` class.**

The factory venv polluting subprocess gates is a real and immediate footgun the moment Phase 5 starts. Cert-watch alone needs FastAPI, SQLAlchemy, APScheduler, plus test dependencies; none of those belong in the factory venv, and running tests against `sys.executable` would either fail or accidentally import the factory's own dependencies. The debate is right that BC-059's `sys.executable -m` fix was correct for Phase 2 and creates a Phase 5 problem.

**Where I diverge:**

The debate proposes a `VenvManager` class with caching, dependency parsing, tool installation, etc. That's the v1 pattern: build the abstraction before the second use case. Reject.

**Concrete shape:**

1. `evaluate_implementation()`, `_run_pytest()`, `_run_mypy()`, `_run_ruff()` accept an optional `python_executable: Path | None = None`. If `None`, fall back to `sys.executable` (today's behavior).

2. The runner (or workspace helper) computes `python_executable` like this:
   ```python
   def project_python(workspace: Path) -> Path | None:
       venv_python = workspace / ".venv" / "bin" / "python"
       return venv_python if venv_python.exists() else None
   ```

3. A workspace helper `ensure_project_venv(workspace, requirements_path)` runs `uv venv` + `uv pip install -r requirements.txt` if the venv doesn't exist or `requirements.txt` hash changed. `uv` is already a transitive dep; no new dependency.

4. Config flag `use_project_venv: bool = False` toggles whether the runner looks for / creates the venv. Default off through Phase 4; flip to on for Phase 5 cert-watch run.

That's it. ~50-80 lines, no new module, no `VenvManager` class, no `pip install` (use `uv` for speed). When the second non-trivial venv use case shows up, the abstraction will be obvious; until then, it's premature.

**Why narrower than the debate:**

- "Per-work-item venv" — no. Work-items in the same project share a venv. If Phase 5 ever has cross-project work-items in one run, revisit.
- "Auto-prune venvs for completed projects" — no. Manual `make clean-venvs` is enough; auto-prune is a footgun (race with replay tests).
- "Cross-platform venv paths" — defer. Linux only is fine for now (per the debate's own mitigation).

**Connection to GR006a:** cert-watch FR-02+FR-03 needs `cryptography` (cert parsing) and likely `httpx` or stdlib for TLS. The 50-line shim must land before GR006a runs, or the gate will fail spuriously on missing imports.
