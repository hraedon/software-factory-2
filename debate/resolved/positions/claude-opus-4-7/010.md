# Position on Debate 010 — Event log retention

**Defer the retention/cold-tier design. Ship the two metrics + an auto-breadcrumb threshold. Revisit when the threshold actually fires.**

The math in the debate is right but the conclusions outrun the data. ~500 events per golden run × 100 golden runs = 50K events total today. Postgres handles that without indexing tricks. The hot/cold tier design is correct *eventually* but building it now is paying maintenance cost on a system that may never reach the regime where it matters — sf2 may pivot to a different storage model before missions hit 10K events per work-item.

**Accept (build now — minimal):**

1. Add a telemetry counter: `event_count_per_work_item` in the existing `telemetry.py` reporter.
2. Add a timing metric: `replay_duration_ms` measured around `sub.replay()` calls in tests / golden runs.
3. CI threshold: if any work-item exceeds 5,000 events OR `replay_duration_ms > 10_000`, auto-file a breadcrumb (`make audit` or a dedicated check). Use thresholds *below* the debate's stated trigger thresholds (10K events, 30s replay) so we have warning before pain.
4. Add `event_count_p50 / p95` to the post-GR telemetry table. Visibility, no enforcement.

That's a half-day of work. It costs nothing if we never reach the threshold and it gives concrete evidence-based numbers when we do.

**Reject (defer indefinitely):**

1. **Cold-tier JSONL.gz archival.** The cold tier introduces: a serialization format independent of regista, integrity checking (SHA-256 manifest), read-path complexity (replay across hot+cold boundary), backup story, and a regista-side hook for archival writes. That's substantial code committed against speculation about what missions will look like.
2. **Regista-level changes.** Same reasoning as Debate 009: don't modify regista for sf2-only pain that hasn't materialized.
3. **Within-Postgres compaction (collapsing heartbeats).** Heartbeats and poll_hooks events being noisy is a different problem with different solutions (filter at read time; don't write them in the first place). Don't conflate.

**On the spec impact:**

Spec.md should note the deferral explicitly, not silently. Add a one-paragraph subsection to §9 (regista) or a new entry in §11 (out of scope) saying "Retention and archival are deferred; the system has no retention policy today and may exceed Postgres capacity at sustained mission lengths >X. Tracked via telemetry; revisit when threshold fires." Future readers should see the gap, not infer it.

**Disagreement with the debate's framing:**

Debate 010 lists "Phase 5+" as blocking. I think it's *never* blocking in the strict sense — the failure mode is degradation (slow replay, growing storage) not correctness. Treat it as ops-debt to be retired when measured, not as a phase gate.

**Replay performance is the actual risk to track.** Storage is cheap; replay latency directly affects test-suite wall-clock and resume time. The debate's 30s threshold for replay is roughly right; my 10s CI threshold gives warning before that cliff.
