# Position on Debate 009 — Event schema evolution

**Accept the consumer-level pilot in sf2. Reject (or rather, defer indefinitely) the substrate-side schema registry.**

The diagnosis is correct: BC-068 is a producer/consumer drift bug at root, and ad-hoc dict shapes will keep producing this class of bug as the event vocabulary grows through Phases 3–5. The structural fix is to make payload shapes typed, validated, and round-trippable. Where I diverge is on *which layer* should hold the schemas.

**Accept (build now):**

The debate's "minimal alternative" is the right approach:

1. `src/factory/event_schemas.py` — dataclasses (or typed dicts) for each event payload sf2 produces: `GatePassPayload`, `GateFailPayload`, `SubmitPayload`, `ChannelFailPayload`, `CannotProceedPayload`. Each has a `to_dict()` and `from_dict()`.
2. `gate_process.py`, `runner.py`, `scheduler.py` use these dataclasses to *construct* payloads. No raw dicts at write sites.
3. `telemetry.py` uses the same dataclasses to *read* payloads. `from_dict` raises on missing required fields.
4. Round-trip CI test: construct each payload type → `to_dict()` → `from_dict()` → assert equal.
5. Replay-against-fixture test (also lands as part of BC-068 fix): real GR004/005 event subset → load via `from_dict()` → assert no validation errors.

This is one focused session. It catches BC-068's class of bug without adding any cross-repo coordination.

**Reject the substrate registry — for now:**

The debate proposes adding `register_payload_schema()` to substrate with warn/strict modes, versioning, and a `payload_schema_warning` flag stored on the event. Reject because:

1. **Single consumer.** sf2 is the only substrate consumer today. Building a schema registry into a shared dependency for a problem only one consumer has hit is exactly the over-coordination v1 fell into.
2. **Append-only invariant.** The debate correctly notes substrate must never reject an event for schema mismatch (it would break append-only). So the registry can only *warn*. But a warning a consumer can already produce in its own `from_dict()` doesn't need to live in substrate.
3. **Version negotiation is a real API surface.** "Give me all gate_pass events with schema_version >= 2" is a non-trivial query interface that needs index design, migration semantics, and versioned event tables. That's a multi-week substrate change for a one-consumer benefit.
4. **The cost of adding it later is overstated.** The debate calls retroactive addition "O(N) work." In practice it's "tag historical events with `schema_version: 1` once" — an `UPDATE` migration, not per-event work.

**Trigger to revisit:** when a *second* substrate consumer exists (audit tool, dashboard, second factory) and they actually disagree about an event shape. Until then, sf2's consumer-level schema is sufficient and substrate stays a thin spine.

**Connection to BC-068:** land the consumer-level schema *as part of* the BC-068 fix, not as a separate item. The fix isn't done until the producer and consumer agree, and that agreement *is* the dataclass.
