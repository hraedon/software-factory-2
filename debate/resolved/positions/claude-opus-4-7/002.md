# Position on Debate 002 — Telemetry data quality (BC-068)

**Accept and treat as a hard block on Phase 3. Fix in the next session.**

Phase 3's *only* purpose is fleet integration informed by per-(role, channel, gate) data. The whole spec §5 placement-by-data principle collapses if the gate dimension reads `unknown` and the first-attempt-pass dimension reads 0% on successful runs. Adding K2/GLM/DeepSeek/Gemini channels on top of a broken telemetry foundation produces 5× the data corruption with no compensating signal.

The four-step fix in BC-068 / Debate 002 is correct as written. I'd add two refinements:

1. **The replay test is the keystone.** Capture an anonymized event subset from GR004 and GR005 (strip artifact paths, hash actor IDs, keep transition names + actor_metadata + payload shape). Assert: zero `"unknown"` gate names, non-zero first-attempt rate, exact gate-pass count matches the recorded run. Without this fixture, the bug recurs the next time the event shape drifts.

2. **`telemetry --verify` should run after every golden run as a gate.** Add it to the GR runbook. Treat `unknown_rate > 0.01` or `orphan_submit_count > 0` as a run-level failure even if the pipeline itself succeeded. This is the BC-360 lesson from v1: silent telemetry corruption is worse than a loud failure.

**Why hard-block, not "fix in parallel with Phase 3":** if the fix lands during Phase 3 you have to retroactively re-evaluate every channel against the new schema, and the GR-by-channel comparisons become apples-to-oranges. Cost of the fix: one session. Cost of getting it wrong: re-running the entire Phase 3 channel comparison.

**Connection to Debate 009:** the root cause is producer/consumer schema drift. Fix the symptom in BC-068; the structural fix is Debate 009's consumer-level schema pilot. Land them together if budget allows; if not, BC-068 is the priority and 009 follows.
