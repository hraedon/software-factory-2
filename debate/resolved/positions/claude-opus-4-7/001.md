# Position on Debate 001 — Behavioral / Playwright gate

**Defer the implementation to Phase 5; draft the spec section now while the talk's reasoning is fresh.**

Building Playwright infrastructure before there's a UI fixture in the curated set is YAGNI. Phase 2/3/4 fixtures are libraries (functions, ADTs, error taxonomies), not apps. Wiring Playwright into `evaluate_implementation()` to run against artifacts that don't have a UI produces no signal and adds a dependency, browser binaries, and flake surface to every gate run.

But Luke's data is the strongest external evidence we have for this gate's necessity ("validation never succeeds on first pass," 60% wall-clock in validation). The thinking should not be lost. Concretely:

1. **Now:** Add a `behavioral_scenarios[]` field to the work-item / spec schema (no consumer yet). Add a `behavioral_gate.py` stub that returns `skip` unless `behavioral_scenarios` is present. Add a one-paragraph subsection to `spec.md` §6 (gates) describing the gate's role and ordering (after mechanical, before frontier judge). Cost: 1 hour.

2. **Phase 5 trigger:** Ship Playwright integration as part of the cert-watch GR006b plan, not before. Cert-watch's FR-01 (dashboard) and FR-02/03 (forms) are the natural pilot.

3. **Generalization concern:** the debate proposes generalizing to "computer use" via a `behavioral_spec` YAML. Reject this generalization until two distinct interaction modes (web + something else) actually exist. Premature abstraction is the v1 pattern.

**Why not build now:** the cost of building a gate with no consumer is the cost of *maintaining* it through Phase 3 and Phase 4 changes without it ever firing. v1 has many such gates that rotted between use.

**Why not defer entirely:** the spec section is cheap to write and the act of writing it now disambiguates ordering (before frontier judge), failure routing (back to implementer with screenshots), and the AC↔scenario binding contract — all of which are easier to design before two more gates land.
