# Position on Debate 005 — Mutation testing

**Accept. Build between Phase 3 fleet completion and Phase 4 jury, not before.**

The reasoning is sound and Luke's quote ("tests written after implementation don't catch bugs, they confirm decisions") is direct external corroboration of spec §8.9's stated risk. The frontier judge is exactly the kind of expensive, probabilistic gate that benefits from a cheap deterministic filter in front of it. v1 had AST-based mutation testing (BC-107/186) for a reason; the lesson should not be relearned.

**Where the debate is right:**

- Custom 10-operator mutator beats `mutmut`/`cosmic-ray`. Heavy mutation libraries are slow and produce many low-value mutants (string literals, dead code in error paths). The proposed operator set is exactly the high-signal set: comparison flips, arithmetic flips, boolean flips, guard deletion, branch swaps.
- Threshold calibrated against curated set, not hardcoded. Treat threshold as data.
- Cache by implementation hash. Critical — without caching, every gate run does N×N work.

**Where I'd refine the timing:**

The debate says "Phase 4 (jury gates) or Phase 5 (first real workload)." I'd narrow that: build it *between* Phase 3 channel completion and Phase 4 jury, so the jury has empirical mutation kill-rate data per channel as one input. Building it before Phase 3 is wasted (the data isn't fed to anything yet); building it after Phase 4 means the jury has to be retrofitted to consume mutation data.

**Concrete sequencing:**

1. Phase 3 completes channel adapters; collect mutation-kill-rate data passively per (channel, work-item) without gating on it.
2. After Phase 3, calibrate threshold from the multi-channel data. Different channels likely produce different test-quality distributions; the threshold should reflect that, possibly per-channel.
3. Phase 4 jury treats mutation kill rate as one signal among (cross-family review, jury vote, mutation rate). Don't make it a hard gate immediately — let the jury weigh it.

**Where I'd push back on the debate:**

The "Replace `0` with `1`, `""` with `"x"`" operator class is high-noise. Many correct functions return constants for legitimate reasons. Start without it; add only if the empirical kill rate suggests insufficient discriminating power.

**Risk the debate undersells:** mutation testing on subprocess gates (pytest) is slow because each mutant requires a fresh pytest invocation. For a 50-test suite × 10 mutants = 500 pytest runs. Even at 2s each, that's 17 minutes per implementation. Mitigation: parallelize mutant runs (one of the few places parallelism is safe — read-only). Or: only mutate functions covered by failing-test heuristics. Decide at implementation time.
