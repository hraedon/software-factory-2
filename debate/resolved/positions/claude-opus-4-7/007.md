# Position on Debate 007 — Credential management

**Accept the YAML schema. Reject rotation detection, key_id audit, and fallback-on-401 routing as premature.**

Phase 3 adds K2 ($7/wk → $49/mo), GLM (z.ai), DeepSeek (Ollama Pro), Gemini CLI. That's 4 providers with ~6 distinct auth modes by the time you count headers, env vars, CLI flags, and subscription tokens. A `credentials.yaml` with per-provider entries is the right minimum and the v1 `Credentials/` raw-text-file pattern is genuinely insufficient at this scale.

**Accept (build now):**

1. `~/.config/factory/credentials.yaml` (XDG path) with the simple shape from the debate.
2. `CredentialsLoader` (function, not class) that reads the file at startup, returns `dict[provider, key]`.
3. `RoleConfig` gains optional `provider: str | None`; if set, runner injects the corresponding key into the channel adapter's invocation env.
4. Channel adapter is responsible for provider-specific injection (Bearer header vs `--api-key` flag vs env var). The credential layer stays generic.
5. `structlog` redaction: any key field redacted to `"<redacted:fk-...****>"` (first 4 chars + ellipsis) in all log paths. Enforce with a CI test that greps logs for known key prefixes.

**Reject (premature):**

1. **Rotation detection via 401 patterns.** Reject. We have no data on what each provider's auth-failure response actually looks like — Fireworks' 401 may not match z.ai's may not match Ollama's. Building a parser before seeing the responses is guessing. When a real auth failure happens in Phase 3, *then* add the matcher for that specific provider's response.

2. **Fallback-on-401 routing to a different channel.** Reject as a Phase 3 deliverable. This is a meaningful behavior change to the router and scheduler; needs spec.md treatment, not a sidecar feature in credential management. File as a post-Phase-3 RFC if it actually becomes painful.

3. **`key_id` hashed audit in telemetry.** Reject. The principal can audit the credentials.yaml file directly — that *is* the inventory. Hashing keys into telemetry events adds noise without solving a real problem (no one is rotating keys per-invocation today).

**Why this scoping:**

The debate's full design is correct in 12 months. Today, the *auth pipe* needs to work and not leak. Everything else is speculation about operational pain we haven't felt. The pattern v1 fell into repeatedly: building the operationally-correct version before the working version, then both sit half-built.

**Risk to flag:** opencode CLI manages its own provider keys via its own config. If we *also* manage them in `credentials.yaml`, there are two sources of truth. Decision needed: either (a) sf2's CredentialsLoader writes through to opencode's config, or (b) opencode-channel role configs declare "use opencode's existing credentials" and skip our injection. I prefer (b) — less coupling — but it means OpenCodeChannel's contract differs from K2/GLM/DeepSeek adapters. Worth discussing before the schema is finalized.
