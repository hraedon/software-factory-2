# Position on Debate 005 — Test efficacy / mutation testing

**Two-stage: ship GLM's assertion-counting gate now (Phase 2). Build mutation gate between Phase 3 and Phase 4, starting with DeepSeek's calibration fixture.**

## Why assertion-counting gate first

GLM identified the right cheap intermediate: count `Assert` AST nodes per collected test file. This catches the most common test-theater pattern (tests that run but never assert) at near-zero cost:
- ~20 lines of code
- <1s per gate run
- No calibration needed
- No subprocess invocations

BC-038 (pytest collectability) already catches zero-test suites. The assertion gate extends the same principle: **a test suite that collects but never asserts is a vacuous contract**. This is the mechanical equivalent of the frontier judge's "do these tests demonstrate the AC is met?" question.

Implementation:
```python
def _count_assertions(test_path: Path) -> int:
    tree = ast.parse(test_path.read_text())
    return sum(1 for node in ast.walk(tree) if isinstance(node, ast.Assert))
```

Gate fails if `assertion_count == 0` or `assertion_count < test_function_count`. Route to `test_author` with diagnostic: "tests exist but contain no assertions."

## Why mutation testing comes later

The debate's 10-operator custom mutator is correct in design but wrong in timing:
- Wall-clock cost is high: 15 impls × 10 operators × 50 tests × 2s = 25 minutes per gate cycle
- Threshold calibration requires multi-channel data (Phase 3)
- The jury (Phase 4) is the consumer of mutation kill-rate data

**DeepSeek's calibration-fixture-first approach is the right sequencing:**
1. Collect 10–15 (impl, test_suite) pairs from GR004/005.
2. Run candidate mutation operators against them.
3. Measure kill rate per operator, per channel.
4. Pick the operator set and threshold from data, not from the debate's recommended list.

Start with 5 operators (comparison, arithmetic, boolean, guard deletion, branch swap) not 10. The `Replace constant` operator class is high-noise; add it only if data shows insufficient discriminating power.

## Risk the debate undersells: parallelization is required

The debate says "cache mutants by implementation hash" but doesn't address the wall-clock problem for new implementations. Even with caching, the first run of a new implementation is slow. The mitigation is parallel mutant execution (read-only, safe). But the gate process (`gate_process.py`) currently processes one work-item at a time. Parallelizing mutants requires either:
- ThreadPoolExecutor within the gate (complexity in gate_process)
- or: limit mutation gate to implementations that already pass all other gates (so the count is small)

Account for this in the Phase 3→4 build.

## Connection to R2-001

The mutation gate's wall-clock cost is a budget risk. If a single implementation triggers 25 minutes of mutation testing and the scheduler re-claims the work-item after timeout, the budget compounds. R2-001's budget breaker should account for gate-process wall-clock, not just model tokens.
