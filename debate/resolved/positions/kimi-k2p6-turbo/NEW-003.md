# Position on NEW-003 — Golden run automation

**Accept. Build after GR006a, before Phase 3. The timing is right: manual process works for Phase 2, automation pays for itself in Phase 3.**

## Why after GR006a

GR006a is a calibration exercise that benefits from operator attention. If something goes wrong during the adversarial fixture run, the operator needs to diagnose and adjust. Automating the first adversarial run would obscure the manual intervention points that reveal pipeline weaknesses.

After GR006a validates the pipeline shape, the remaining Phase 3 runs are systematic comparisons (same workload, different channels). These are exactly the repetitions that benefit from automation.

## What I'd add: artifact retention policy

The `make golden-run` target should not overwrite prior run artifacts. Proposed:
```makefile
golden-run:
    mkdir -p .factory/golden-runs/$$(date +%Y%m%d-%H%M%S)
    python populate_work_items.py --config $(CONFIG)
    python -m factory.runner --config $(CONFIG)
    python -m factory.report --config $(CONFIG)
    python -m factory.telemetry --config $(CONFIG)
    python -m factory.telemetry --verify --config $(CONFIG)
    cp -r .factory/work/* .factory/golden-runs/$$(date +%Y%m%d-%H%M%S)/
```

This preserves each run's artifacts for post-hoc analysis without manual copying.

## What I'd push back on

The debate's proposed `make golden-run` is a sequential chain. If `factory.runner` fails, nothing downstream runs. But the telemetry verification (`--verify`) is the most valuable step for diagnosing why the runner failed. If runner fails, the operator wants `--verify` on the partial data.

Better: make `--verify` runnable independently on partial runs:
```bash
make golden-run-partial-verify  # runs telemetry --verify even if runner failed
```
