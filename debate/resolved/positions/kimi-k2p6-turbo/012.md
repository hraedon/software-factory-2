# Position on Debate 012 — Attempt-level latency tracking

**Accept. The spec requires it (§7), the implementation lacks it, and Phase 3 needs it. But normalize latency by spec complexity, not just raw wall-clock.**

## Why raw wall-clock is insufficient

GR004 took ~31 minutes, GR005 took ~52 minutes. The naive interpretation: Sonnet is 40% faster. But:
- The two runs used different prompt versions (BC-039 changed between them)
- The two runs may have had different spec fixtures (verify this)
- The two runs ran on different days with different system load

Raw wall-clock conflates channel speed with prompt complexity, system load, and fixture difficulty. For fleet placement, we need **normalized latency**: wall-clock per acceptance-criterion, or wall-clock per spec text length.

## Proposed design

1. **Record raw wall-clock:** `invocation_start_time` / `invocation_end_time` in `actor_metadata` (as proposed).
2. **Compute normalized latency in telemetry:** `duration_seconds / ac_count` for the work-item's spec section. This gives "seconds per acceptance criterion" — comparable across different spec sizes.
3. **Report both:** raw mean/median for mission-time estimation; normalized for channel-quality comparison.
4. **Per-channel timeout:** Accept the debate's proposed `per_channel_timeout` config. But default it to `None` (backward compatible) and populate it from Phase 3 telemetry data, not from GR004/005 alone.

## Why normalization matters

If implementer role runs on:
- Claude: 90% pass rate, 45 min, 15 ACs → 3.0 min/AC
- GLM: 85% pass rate, 15 min, 15 ACs → 1.0 min/AC

The raw data says Claude is 3× slower. The normalized data says Claude is 3× slower per AC. But if the next mission has 30 ACs, GLM finishes in 30 minutes and Claude in 90. The principal needs both numbers to decide.

## What I'd push back on

The debate's proposed `per_channel_timeout` is valuable but should not be populated from two data points (GR004/005). Wait until Phase 3 has 4+ channels × 15 work-items = 60 data points, then set timeouts at p95 + 20% margin.

## Blocking

Phase 3. Not strictly blocking (fleet can be placed on pass rate alone) but placement quality is materially worse without latency data. Build alongside BC-068 and Debate 011.
