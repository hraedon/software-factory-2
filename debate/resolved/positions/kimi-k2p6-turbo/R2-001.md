# Position on R2-001 — The 'Infinite Spend' Circuit Breaker

**Strong accept. Pair with R2-005 (notification hook). Budget breaker without notification is silent failure; notification without budget breaker has nothing important to alert on.**

## Why this is not just a v1 feature port

v1 had a "Global Budget Breaker" with token tracking. v2's architecture is different: flat-rate subscriptions for most channels (Claude Code, OpenCode), API keys for others (K2 at $7/week). The economics changed, but the risk didn't.

The real risk in v2 is not token spend — it's **wall-clock retry loops**. A stuck work-item with `attempt_threshold = 3` that fails at the mechanical gate each time consumes:
- 3 × model invocation time (5–15 minutes each)
- 3 × gate evaluation time (pytest, mypy, ruff)
- 3 × scheduler re-creation time

For 15 work-items in a 3-stage pipeline, a systematic failure mode (e.g., all implementations fail import gate because of a missing venv dependency) burns hours of wall-clock before anyone notices.

## Proposed design: wall-clock budget, not token budget

1. **`FactoryConfig.max_mission_wall_clock_minutes`** — total mission budget. Default: 180 minutes (3 hours) for a 15-item GR.
2. **`FactoryConfig.max_work_item_attempts`** — per-item hard ceiling. Default: 5 (above current `attempt_threshold = 3`).
3. **Scheduler check:** Before creating a new work-item or transitioning a failed item to `new`, check elapsed wall-clock. If exceeded, force-transition all active items to `cannot_proceed` with `budget_exhausted` reason.

The scheduler is the right place for this check because it owns the orchestration loop and has visibility into all work-items.

## Why pair with R2-005

A budget breaker that silently halts the pipeline defeats the purpose of asynchronous autonomy (Luke's "approve the plan, then go do something else"). The operator needs to know the pipeline stopped and why.

R2-005 proposes a notification sink for escalation events. R2-001's `budget_exhausted` should be the first event type wired to that sink. Together they form a complete failure mode: detect → alert → stop.

## What I'd push back on

The debate's proposed `cost_estimate = tokens × $/token_per_provider` table is a rabbit hole. Token counts are unreliable (prompt caching, output streaming, tool use). Flat-rate channels have no marginal cost. The right metric is **wall-clock time** — it's measurable, comparable across channels, and directly correlated with operator attention.

## Concrete next step

1. Add `max_mission_wall_clock_minutes` and `max_work_item_attempts` to `FactoryConfig`.
2. Add budget check to `scheduler.py` before handoff creation and before re-queueing failed items.
3. Emit `budget_exhausted` event with diagnostics: elapsed minutes, items completed, items pending.
4. Wire to R2-005 notification sink.
5. ~50 lines total.

## Blocking

Phase 3 (fleet integration). Must land before multi-channel runs, because K2 API + Claude Code + GLM + DeepSeek + Gemini running in sequence or retry chains can compound wall-clock costs.
