# Position on Debate 008 — Golden-run fixture representativeness

**Strong accept. Run before declaring Phase 2 complete. DeepSeek's test-as-criteria approach makes the threshold machine-enforceable.**

## Why this is load-bearing for Phase 2 exit criteria

The current metric — "87% implementation pass rate on 15 curated fixtures" — is the right metric for the wrong population. The 15 fixtures are self-contained, behavior-testable, and likely well-scoped. Factory's production data (Luke's talk) shows real workloads are:
- Multi-module (cross-imports)
- Stateful (database, filesystem)
- UI-driven (forms, buttons, navigation)
- Integration-heavy (3+ modules must work together)

If 87% on curated fixtures drops to 40% on a realistic workload, the Phase 2 metric is a vanity number. The principal would be misled into declaring Phase 2 done when the pipeline is not ready for real work.

## The adversarial fixture should have 5 characteristics

1. **Multi-module dependency:** Interface spec declares 3+ modules. Tests exercise integration. Implementation must wire them.
2. **Stateful behavior:** Requires SQLite or file operations. Tests verify persistence.
3. **Error taxonomy:** 5+ error conditions with explicit test coverage.
4. **UI component:** FastAPI endpoint with a form. The behavioral gate (Debate 001) exercises it.
5. **AC ambiguity:** One acceptance criterion is intentionally vague. The system should escalate or resolve.

## Why test-as-criteria beats a markdown table

The debate proposes a 3-outcome table (pass → proceed, drop 30+ points → add intermediate fixtures, catastrophic → redesign). DeepSeek's improvement: encode the threshold as an asserted test:

```python
def test_gr006a_criteria():
    result = run_golden_run(fixture="adversarial_5_feature")
    assert result.interface_spec_pass_rate >= 0.90
    assert result.test_suite_pass_rate >= 0.90
    assert result.implementation_pass_rate >= 0.60  # calibrated
```

This makes the threshold machine-enforceable. The principal cannot accidentally proceed to Phase 3 with sub-threshold data. The test is the gate.

## What I'd add: measure time-to-first-failure

The debate focuses on pass rate. But another important metric is **where the first failure occurs:**
- Interface spec failures = upstream ambiguity
- Test suite failures = contract weakness
- Implementation failures = implementation quality
- Gate failures = test or implementation quality

If the adversarial fixture fails primarily at the interface_spec stage, the problem is spec quality, not implementation. This is actionable data for the socratic-specification process.

## Sequencing

1. **Day 1:** Author the adversarial fixture (FastAPI + SQLite + 3 modules + error taxonomy + vague AC). 1 session.
2. **Day 2:** Run GR006a with current best channel (Kimi k2.6 or Claude Sonnet).
3. **Day 3:** Apply threshold. If impl pass rate > 60%: Phase 2 close. If 40–60%: add intermediate fixtures. If < 40%: redesign pipeline before Phase 3.
