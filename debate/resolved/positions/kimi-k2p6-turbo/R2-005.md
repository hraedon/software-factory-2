# Position on R2-005 — Operator UX and Asynchronous Interrupts

**Accept minimally. Build a notification event sink for `cannot_proceed` and `budget_exhausted` events. Defer full dashboard to Phase 5+.**

## Why the minimal version is load-bearing

The Factory talk (Luke) makes the value proposition explicit: "approve the plan, then go do something else." sf2 currently has no mechanism for "something else" — the operator must poll the CLI or check the worklog to discover that the pipeline stopped.

If the pipeline hits an escalation (BC-068 fixed, attempt_threshold exceeded, spec ambiguity, budget exhausted), the principal must know. The regista event log is the source of truth, but it is not a push notification system.

## Proposed minimal design

1. **Event hook in regista:** `register_hook_handler("escalation", fn)` where `escalation` is a synthetic event type emitted by the scheduler when any work-item transitions to `cannot_proceed`.

2. **Notification adapter interface:**
   ```python
   class NotificationSink(Protocol):
       def notify(self, title: str, body: str, urgency: str) -> None
   ```

3. **Built-in adapters:** `WebhookSink` (POST to URL), `SlackSink` (incoming webhook), `LogSink` (structlog at warning level). Each adapter is ~20 lines.

4. **Configuration in `FactoryConfig`:**
   ```yaml
   notification:
     sink: webhook
     url: https://hooks.slack.com/...
     events: [cannot_proceed, budget_exhausted]
   ```

5. **Actionable content:** Each notification includes:
   - Work-item ID and type
   - Reason (gate name, diagnostic summary, budget status)
   - Suggested command: `factory-report --work-item-id <id>` or `factory-logs --work-item-id <id>`

## Why defer the dashboard

A full "Mission Control" dashboard (per Luke) is valuable but requires:
- A web server (FastAPI/Flask)
- Real-time event streaming (WebSockets or SSE)
- Authentication
- Persistent session state

That's a product, not a pipeline feature. sf2's constraint is that the principal is a systems architect who reviews specs and outcomes, not a developer who debugs code. A notification with an actionable link provides the outcome-level view without the engineering investment.

## What I'd push back on

The debate's proposed "adapter framework for Slack/Discord/Email" implies multiple adapters. Start with one (`WebhookSink` covers Slack, Discord, and generic integrations). Add Email only if the principal uses it. Each adapter adds test surface; don't build adapters for platforms the principal doesn't use.

## Connection to R2-001

R2-001 (budget breaker) and R2-005 should land together. The budget breaker emits `budget_exhausted` events; the notification sink delivers them. One without the other is incomplete.

## Concrete next step

1. Add `NotificationSink` protocol and `WebhookSink` implementation (~40 lines).
2. Wire into scheduler's `cannot_proceed` transition path.
3. Add `FactoryConfig.notification` schema.
4. Test with a local HTTP echo server.
5. Land with R2-001 in the same session.
