# Position on Debate 002 — Telemetry data quality (BC-068)

**Hard-block Phase 3. Fix in the next session. The bug is worse than the debate frames it.**

Four models independently assessed this as a blocker (claude: hard-block, gemini: blocker, glm: hard-block, deepseek: fix + replay test). That's unanimous consensus on the action. But the framing matters: this is not just a data-quality bug — it is a **schema drift failure** between the event producer (`gate_process.py`) and the event consumer (`telemetry.py`).

## Why schema drift, not just bad matching

The `collect_gate_attempts()` logic pairs `submit` events with `gate_pass`/`gate_fail` events by `work_item_id` and then extracts `gate_name` from `actor_metadata` → `payload` → `custom_fields` → fallback `"unknown"`. This is a hand-written extraction heuristic that guesses where the producer put the field.

If the producer changes where it writes diagnostics (and it has — `gate_process.py` writes to both `payload` and `custom_fields`), the consumer breaks silently. The consumer does not fail — it produces degraded data that looks plausible. This is the v1 BC-360 pattern: *telemetry event shape drift produces silent data corruption*.

## The fix must include schema validation

The four-step fix in BC-068 (add `gate_name` to actor metadata, update collector, add data-quality test, add `--verify` CLI) fixes the symptom. But the structural cause is that **producer and consumer share no contract** for what fields exist and where they live.

**My addition to the fix:**

1. **Ship BC-068 as written** (1 session, 2–3 tests).
2. **Simultaneously ship Debate 009's consumer-level schema pilot** (`factory/event_schemas.py` with dataclasses for each event type). The telemetry collector should construct schema instances from events, not extract fields by string key.
3. **The golden-run replay test becomes a schema-roundtrip test:** parse event → construct schema instance → serialize → assert equal. If the schema class is missing a field, the test fails. If the producer puts the field in the wrong place, the test fails.

## Why this matters for Phase 3

Phase 3 adds 4 new channel adapters. Each adapter may introduce new `actor_metadata` fields (model version, provider-specific cost, prompt hash). Without a schema contract, the telemetry collector will silently drop these fields or misclassify them as `"unknown"`.

The cost of fixing BC-068 now: 1 session.
The cost of discovering the same bug after 4 channels are live: re-run all golden runs, re-calibrate all thresholds, lose 2–3 sessions of data.

## Connection to Debate 009

These are the same fix at different layers. BC-068 fixes the immediate symptom; Debate 009 prevents recurrence. Land BC-068 first. If budget allows, land the consumer-level schema pilot in the same session. If not, schedule 009 for the following session — but do not let Phase 3 begin before both are in place.

## What I'd push back on

The debate's proposed `telemetry --verify` mode should not be a manual post-run check. It should be a **CI gate** that runs after every golden run. If `unknown_rate > 0` or `orphan_submit_count > 0`, the CI job fails. Manual checks get skipped; CI gates don't.
