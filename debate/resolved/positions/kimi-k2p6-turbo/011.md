# Position on Debate 011 — Prompt versioning in telemetry

**Accept. This is the same class of problem as BC-068: silent data corruption that makes cross-run comparisons invalid. Build alongside BC-068 in the same session.**

## Why this is not optional

GR004 (Claude Sonnet) and GR005 (Kimi k2.6) show a 7-point implementation pass rate difference. The telemetry attributes this to the channel. But BC-039 updated the implementer prompt with modern typing conventions between runs. Was the improvement due to Kimi being better at lint-passing code, or due to the prompt now teaching modern typing? The data cannot answer this question.

Phase 3 will compare K2/GLM/DeepSeek/Gemini against the GR004/005 baseline. If the baseline was produced with an older prompt version, the comparison is confounded. Fleet placement decisions built on confounded data are wrong by construction.

## Why content hash beats git hash

DeepSeek's position proposes `git log -1 --format=%h`. GLM's position proposes SHA-256 of file content. The content hash is better because:
- Git hash requires a git repository (always true here, but fragile)
- Content hash works even if the file is moved or renamed
- Content hash is tamper-evident: if someone edits the file without committing, the hash changes

Use SHA-256 of the template file content. Truncate to 8 characters for display.

## Why this pairs with BC-068

Both are telemetry data-quality prerequisites for Phase 3. Both touch `telemetry.py` and `ActorMetadata`. The fix for BC-068 adds `gate_name` to actor metadata; the fix for 011 adds `prompt_template_hash`. One session, ~40 lines total.

## What I'd add: prompt diff on hash mismatch

When the telemetry report detects multiple hashes for the same (role, channel), it should not just warn — it should offer to diff the prompt files:
```
Warning: implementer prompt changed between runs.
  GR004: hash=a3f7e2d1
  GR005: hash=b8c9d4e2
  Diff: git diff a3f7e2d1..b8c9d4e2 -- prompts/implementer.md
```
This makes the confounding variable visible and actionable.

## What I'd push back on

The debate says "group pass rates by (role, channel, family, gate_name, prompt_template_hash)." For Phase 3, this fragments the table: if the prompt changes once during the phase, every channel has two rows (old hash, new hash). A cleaner approach: treat the most recent hash as the canonical comparison point, and flag older hashes with a "stale" marker. The principal can then decide whether to re-run the baseline with the new prompt.
