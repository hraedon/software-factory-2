# Position on Regista Debate 002 — Workflow composition

**Defer. Phase 2 YAML is 80 lines. Phase 4 YAML is a guess. Adding `!include` for a problem that hasn't happened is premature.**

The debate projects a 200-line YAML file for Phase 4. That's a forecast, not data. The spec defers composition out of scope — maintain that deferral until you have a concrete YAML file that's actually painful to edit.

**My position:**

1. **Write the Phase 4 YAML on paper before implementing composition.** The debate says to draft `phase4.yaml` and if it exceeds 150 lines, implement `include`. That's the right approach, but I'd strengthen it:
   - Draft the FULL Phase 4 YAML inline (not fragments), with every state, transition, role, and work_item_type.
   - Measure: line count, nesting depth, number of transitions.
   - If writing the draft takes less than 1 hour, the composition problem is small. If it takes 3+ hours and you make YAML syntax errors along the way, the problem is real.

2. **Add the linting threshold FIRST.** `make lint-workflow` that fails if a workflow YAML exceeds 150 lines or 5 nesting levels. This is 30 lines of Python. If Phase 2 YAML is 80 lines, the lint passes. If Phase 4 YAML is 200 lines, the lint fails and THAT triggers the composition implementation — not a forecast, an actual failure.

3. **The `include` primitive is the right design but wrong timing.** The debate's proposed `include:` list with last-wins semantics is correct. But building it now (Phase 2) means maintaining `include` parsing, circular detection, and composition validation through Phases 3 and 4 without any actual multi-file workflows. That's paying maintenance tax on unused infrastructure.

**Disagreement with the debate:**
- "The principal cannot review a 200-line YAML for correctness." True. But the principal also cannot review 6 × 40-line YAML fragments for correctness. Composition trades one review problem (long file) for another (cross-file consistency). The solution to unreviewable YAML is not composition — it's machine validation (`validate_yaml` already exists per BC-061).
- "Agents struggle with YAML syntax (v1 BC-022)." Also true. But agents struggle MORE with cross-file dependencies (v1 BC-058 in regista's own breadcrumbs). Composition increases the agent failure surface.

**What I'd do:**
1. Add `lint-workflow` target to Makefile (150-line threshold, 5 nesting levels). 30 lines.
2. When Phase 4 planning begins, draft `phase4.yaml` inline.
3. If it exceeds the lint threshold, implement `include` primitive then.
4. Not before.
