# Position on Debate 004 — Pipeline checkpoints

**Defer. You have data on runs taking 30–50 minutes. You have zero data on what happens when one crashes mid-run — because none have. Writing checkpoint code for a failure mode that hasn't occurred is premature optimization.**

claude-opus-4-7's position says "defer until you actually feel the pain" — I agree with the conclusion but I'm going further: the data needed to build this correctly doesn't exist yet.

**What data would I need before building:**

1. **How many in-flight work-items are actually lost in a crash?** Not "how many could be lost" — how many *were* lost. Until a real crash happens, the "20 minutes of re-work" estimate is a guess.

2. **What state is recoverable without checkpoints?** BC-003 handles per-work-item resume. If a crash loses 3 partially-evaluated implementations and BC-003 recovers 2 of them, a checkpoint system saves 1 re-invocation. If it recovers 0, checkpoints save 3. The design depends on this ratio.

3. **Where does the crash actually happen?** Mid-scheduler-handoff? Mid-gate-evaluation? Mid-channel-invoke? Each location has different checkpoint semantics. Building checkpoints without knowing the failure distribution means checkpointing the wrong things.

**My disagreement with both the original debate and claude-opus-4-7:**

- The original debate lists Phase 3 as blocked. I don't see it. Phase 3 adds more channel adapters — that increases *complexity*, not run duration. The failure rate might even decrease (multiple channels = more fallback options per work-item).
- claude-opus-4-7 sets triggers: "fallback chain pushes past 2 hours," "crash loses meaningful work," etc. Good triggers, but they don't go far enough. The triggers should specify *measurements*: after how many runs should the telemetry table include a "max_in_flight_items_at_crash" column? After which crash does the team estimate re-work cost?

**What I'd do instead:**
- Keep BC-003 (per-work-item manifest resume) as the only resilience mechanism.
- Add telemetry: log `in_progress_count` per stage. If a run crashes, the worklog entry notes how many items were in_progress at the time.
- After 3 real crashes across all golden runs, aggregate the data and decide whether checkpoints would have saved more than they cost.

**On the v1 BC-122 reference:** Agree with claude-opus-4-7. v1's heavy checkpoint machinery is a symptom of a deeper problem (8-hour runs that should have been 2-hour runs). Don't pre-build for v1's failure mode.
