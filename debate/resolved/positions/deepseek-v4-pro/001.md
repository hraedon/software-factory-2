# Position on Debate 001 — Behavioral / Playwright gate

**Reject the "stub-only now" strategy from claude-opus-4-7. Build the stub, yes — but also write *one concrete Playwright test against a real fixture* and let it *fail*. Then you know what you're building toward.**

claude-opus-4-7's position (defer implementation, write spec section now) treats the spec as the artifact and the implementation as deferred work. My concern: a spec section with no verifying test is indistinguishable from a wish. The debate's core claim — "validation never succeeds on first pass, 60% wall-clock in validation" — is a statement about *behavior*, and it deserves a behavioral test to validate it.

What I'd do differently:

1. **Write one concrete Playwright test now against an existing fixture.** Pick cert-watch FR-01 (dashboard) or a simple FastAPI "hello world" endpoint. Write a Playwright script that launches the app, loads a page, and asserts something. Run it from a subprocess gate — same pattern as `_run_pytest()`. If it fails (which it will, because cert-watch isn't built yet), the test *is* the spec.

2. **The failing test is more valuable than the spec section.** A spec section says "here's what we'll do." A failing test says "here's what we need to make pass." The latter drives implementation; the former gathers dust.

3. **If writing the test takes more than 1 hour, reduce scope until it doesn't.** The risk is over-engineering the behavioral gate before a concrete workload exists. The mitigation is not to defer entirely — it's to write the smallest test that demonstrates the gap.

**Why this differs from both original debate and claude-opus-4-7:**
- Original debate says: build the full gate now
- claude-opus-4-7 says: write spec only, defer implementation
- I say: write the spec + one concrete failing test. The test is the accountability mechanism.

**The test I'd write:**
```python
def test_behavioral_gate_detects_broken_app(project_workspace):
    """A Playwright test against a deliberately broken FastAPI app.
    Assert the gate fails with diagnostics containing a screenshot path."""
    # This test lives in tests/ and runs via pytest.
    # When the behavioral gate exists, this test passes.
    # Today it fails — and that failure is a breadcrumb itself.
    pass
```

**On generalization to "computer use":** Agree with claude-opus-4-7: reject until two distinct interaction modes exist. Two refactors of clean code beat one over-engineered abstraction.
