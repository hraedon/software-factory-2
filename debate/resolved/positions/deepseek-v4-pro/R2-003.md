# Position on R2-003 — Database migration strategy

**Accept. The migration gate is load-bearing. My addition: the gate's correctness depends on a round-trip test — model → migration → apply → verify. This test is the hard part.**

LLMs are bad at migrations. The debate's insight is correct: don't let the implementer hallucinate `ALTER TABLE` SQL. Use Alembic's `--autogenerate` as a deterministic tool, run by a dedicated gate, validated against a populated test database.

**Where I add to claude's recommendation:**

1. **The round-trip test IS the migration gate.** Before building the gate, write:

   ```python
   def test_alembic_migration_round_trip():
       """Model definition → autogenerate migration → apply → verify schema."""
       # 1. Start with an empty database
       # 2. Write SQLAlchemy models (generated by implementer)
       # 3. Run alembic revision --autogenerate
       # 4. Run alembic upgrade head
       # 5. Assert all tables exist with correct columns
       # 6. Insert test data and query it back
   ```

   This test exercises the full migration lifecycle. If the implementer's models are wrong, the migration fails. If the migration is destructive (drops tables), the test catches it because step 3→4 includes an existing schema.

2. **The migration gate runs as a subprocess gate, same pattern as pytest.** `_run_alembic_check()` in `gate.py`. If `alembic upgrade head` fails → gate_fail with structured diagnostics. If models exist but no migration directory → `cannot_proceed` with "migration not generated."

3. **The migration gate should validate against the PREVIOUS schema.** This is the hard part: the test needs a "before" state. The simplest approach: store the previous implementation's migration in the work-item directory. Apply it to a temp database. Then apply the new migration. If the new migration is destructive, the test fails on the apply.

4. **Phase 5 cert-watch GR006b IS gated on this.** claude is right. cert-watch FR-02+FR-03 may need a `certificates` table. Without a migration gate, the implementer will `CREATE TABLE IF NOT EXISTS certificates (...)` in the implementation code and call it a day. That works once and breaks on every subsequent change.

**The implementation should be:**
1. `test_alembic_round_trip.py` — the test (30 lines)
2. `gate.py:_run_alembic_check()` — the subprocess gate (20 lines)
3. `constants.py` — `GATE_NAME_IMPLEMENTATION_ALEMBIC` (1 line)
4. Wired into `evaluate_implementation()` behind a `requires_database: bool` flag on the work-item (10 lines)

**Total: ~60 lines + Alembic as a dev dependency. Cost: half a day.**
