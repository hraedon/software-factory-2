# Position on Debate 002 — Telemetry data quality (BC-068)

**Fix now before you touch anything else. My colleague is on BC-068 — my position is: don't layer new work on a broken foundation. Write the replay test first, fix second, verify third.**

BC-068 is a "known false-negative" bug: the telemetry system produces garbage data but doesn't know it, and unit tests don't catch it because they test synthetic event shapes against themselves. The fix must include the test that would have caught it — a replay test against real golden-run event fixtures.

**My additions to the four-step fix:**

1. **Write the replay test FIRST, before you touch any production code.** Extract anonymized event data from GR004/GR005. Write `test_telemetry_replay_on_golden_run_fixtures` that:
   - Deserializes real events via the existing `from_dict()` (or direct dict access if no schema exists)
   - Asserts `gate_name != "unknown"` for all gate_pass/gate_fail events
   - Asserts `first_attempt_pass_rate > 0` for at least one (role, channel) pair
   - Runs this test as part of `make test` (not a separate slow suite)
   - If the fixture is too large, sample N=50 events — enough to exercise the matching logic

   This test WILL FAIL today. That's the point. The test documents the bug.

2. **Then fix the code.** Add `gate_name` to actor metadata in `gate_process.py`. Update `collect_gate_attempts()`. The replay test goes green.

3. **Add `telemetry --verify` as a Makefile target.** `make verify-telemetry` reads live substrate, reports `unknown_rate` and `orphan_submit_count`. Non-zero = CI failure.

4. **Run `make verify-telemetry` after every golden run.** Automate it in the GR runbook.

**Why "write test first" matters:**
- Without a replay test, the fix is validated by looking at GR output manually. That's not a fix, it's a bandage.
- The replay test is the regression guard. Next time the event shape drifts (and it will, per Debate 009), this test fails and you know immediately.
- claude-opus-4-7's position calls the replay test "the keystone" — I agree, but I'd go further: it's the FIRST thing you write, not a follow-up.

**Disagreement with claude-opus-4-7:** Their position says "Fix in the next session." I say: fix as soon as the colleague doing BC-068 is available, and write the test before touching the code. The sequencing matters.
