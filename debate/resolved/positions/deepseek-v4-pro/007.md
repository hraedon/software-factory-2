# Position on Debate 007 — Credential management

**Accept the YAML schema plus a redaction test. Reject rotation detection, routing, and audit machinery.**

The schema itself is necessary — Phase 3's 4 new providers need a single place for API keys that isn't scattered across env vars. But every piece of machinery beyond "read key, redact in logs" is a solution to a problem that hasn't happened.

**My additions to claude-opus-4-7's accept list:**

1. **Write a redaction test, not a redaction implementation.** Before writing the log redaction code, write `test_no_credentials_in_logs()`:
   - Configure a channel adapter with a known API key
   - Invoke the adapter (or mock invoke + log)
   - grep the log output for the key
   - Assert zero matches
   This test FAILS today. Fix it. The test is the accountability mechanism — it stays in CI permanently.

2. **The schema should include an explicit `active: bool` field per provider.** Not for rotation detection (rejected) but for the principal to disable a provider without deleting its key configuration. "I want to stop using K2 for a week" should be one YAML edit, not a key rotation.

3. **OpenCode's credentials: document the dual-source problem, don't solve it yet.** claude-opus-4-7 flags the risk that opencode manages its own provider keys separately. Their option (b) — "use opencode's existing credentials" — is correct. But this means OpenCodeChannel's contract differs from K2/GLM/DeepSeek. Add a comment in the credential loader: `# OpenCode channel does not consume credentials.yaml; opencode CLI manages its own provider keys.`. This is documentation, not code.

**Where I disagree with both the debate and claude-opus-4-7:**

- **The debate proposes `CredentialManager` class.** Reject. A `load_credentials(path) → dict` function is sufficient. A class implies lifecycle (reload, invalidate, rotate) — none of which should exist yet.
- **claude-opus-4-7 proposes `CredentialsLoader` function.** Accept the function, reject the name. A factory function with a class-sounding name is confusing. Call it `read_credentials_yaml(path: Path) → dict[str, dict]`.
- **"Reject rotation detection."** claude-opus-4-7's reasoning is correct but incomplete. They say "no data on what each provider's auth-failure response looks like." I'd add: rotation detection is *testable* — write a test that mocks a 401 response and asserts the runner logs `auth_error` with the correct provider name. The test tells you whether you need the machinery. If the test takes more than 20 lines, the machinery is too complex.

**What I'd actually ship:**
1. `credentials.yaml` schema (XDG path)
2. `read_credentials_yaml()` — function, 20 lines
3. `test_no_credentials_in_logs()` — test, 30 lines
4. `test_credentials_loaded_for_channel()` — test that mocks a channel invoke and asserts the key was passed to the environment
5. Nothing else.
