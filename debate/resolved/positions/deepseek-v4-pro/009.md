# Position on Debate 009 — Event schema evolution

**Accept the consumer-level pilot. The value is the round-trip test, not the dataclass definitions. Reject regista registry as premature for single-consumer.**

The debate correctly identifies the root cause of BC-068. claude-opus-4-7's consumer-level approach is correct. My refinement: the round-trip test IS the schema.

**My position:**

1. **Write the round-trip test first.** Before defining any `GatePassPayload` dataclass, write:
   ```python
   def test_event_payloads_round_trip():
       """Every event payload type must survive to_dict() → from_dict() with no loss."""
       for payload_cls in ALL_PAYLOAD_CLASSES:
           instance = payload_cls.example()  # factory method with valid defaults
           serialized = instance.to_dict()
           deserialized = payload_cls.from_dict(serialized)
           assert deserialized == instance
   ```
   This test fails because the dataclasses don't exist yet. The test IS the spec for what the dataclasses must do.

2. **Write the replay-against-fixture test.** As part of BC-068 fix:
   ```python
   def test_gr004_events_validate_against_schema():
       """Real events from GR004/005 must deserialize without errors."""
       events = load_anonymized_gr004_events()
       for event in events:
           if event.transition in SCHEMAS_BY_TRANSITION:
               SCHEMAS_BY_TRANSITION[event.transition].from_dict(event.payload)
   ```
   This test catches schema drift immediately, not after telemetry corruption has already happened.

3. **Reject the regista-level registry — with a concrete trigger.** claude-opus-4-7 says "when a second regista consumer exists." I agree but I'd make it more specific: "when a second consumer *that produces the same transition type with a different payload shape* exists." If two consumers both produce `gate_pass` events but disagree about what goes in the payload, that's the trigger. A second consumer that uses completely different transition types is irrelevant.

4. **On the "version negotiation" argument in the debate:** The debate wants `register_payload_schema(transition, version, schema)` with query-by-version. This is a non-trivial API surface. My counter: the consumer-level dataclass already provides `from_dict()` which is effectively `schema.validate(dict)`. The only thing regista adds is global registration and query-by-version. Neither is needed today.

**Where I differ from claude-opus-4-7:**
- They say "land consumer-level schema *as part of* the BC-068 fix." I agree with bundling but I'd reverse the dependency: BC-068 is the symptom; the schema dataclass is the root-cause fix. Ship the schema fix first (because it prevents recurrence), then verify BC-068 is resolved (because the replay test now works).
- They say "one focused session." I think it's half a session. The dataclasses are 5 minutes each; the test is 15 minutes. Bundled with BC-068, total: 1 session for both.

**The one risk I'd flag that nobody else mentions:**
The schema dataclasses create a new source of truth for event shapes. If someone adds a field to the dataclass but forgets to update `gate_process.py`, the dataclass and the actual payload diverge — the same bug in a different layer. Mitigation: the round-trip test uses the SAME code path (`to_dict()`) that `gate_process.py` uses. If the test passes, the dataclass and the producer agree.
