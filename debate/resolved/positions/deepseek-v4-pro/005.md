# Position on Debate 005 — Mutation testing

**Accept. Build it before Phase 4 jury, but write the calibration fixture first — don't build a gate without knowing what "passing" means.**

The debate's reasoning is correct: mutation testing is a cheap, deterministic filter that catches tautological tests (the exact failure mode spec §8.9 worries about). claude-opus-4-7's sequencing (build between Phase 3 and Phase 4) is correct. My additions:

**What I'd build differently:**

1. **The calibration fixture is not optional.** Before implementing ANY mutator operators, collect 10–15 existing locked (implementation, test_suite) pairs from GR004/005. Run them through the mutation gate manually (or with a one-off script). Record the kill_rate distribution. Now you know:
   - Which operators discriminate (high variance in kill rate across pairs)
   - Which operators are noise (constant 0% or constant 100%)
   - A defensible threshold (25th percentile, or mean minus one stddev)

2. **Start with 5 operators, not 10.** claude-opus-4-7 pushes back on the "replace 0 with 1" operator. I'd go further: start with the 4 comparison/boolean operators (==→!=, >→<, if/else swap, and→or, True↔False). Run the calibration fixture. If kill_rate variance is too low to discriminate, add operators one at a time. Each addition is justified by data from the previous subset.

3. **Caching is table stakes.** Cache mutants by (implementation_hash, operator). The mutation gate is useless if it takes 17 minutes per implementation (claude-opus-4-7's estimate). The first invocation is slow; subsequent invocations hit cache.

4. **The mutation gate should produce telemetry, not just pass/fail.** The telemetry table gains `mutation_kill_rate` per (role, channel, work_item). The jury consumes this as one signal. The gate itself can be advisory initially (log the rate, don't block) and flip to hard-gate after calibration.

**Where I disagree with claude-opus-4-7:**
- They say "start without the 0→1/""→"x" operator class." I say: measure it. The calibration fixture tells you if it's noise. Don't reject operators on vibes — reject them on data.
- They worry about 17-minute mutation runs. I worry less: caching + parallelism covers this, and the gate only runs on implementations that already passed mechanical gates (so most implementations don't reach it).

**What I'd actually build in the first session:**
1. `mutation_operators.py` — 5 operators as pure functions: `apply(ast_node) → ast_node`
2. `mutation_runner.py` — apply all operators, run test suite against each mutant, compute kill_rate
3. `tests/test_mutation_gate.py` — calibration test: run against 5 known GR004/005 pairs, assert kill_rate > threshold (empirically determined from calibration fixture)
4. No integration with `evaluate_implementation()` yet. The gate is standalone, testable, and produces data. Integration happens in session 2.
