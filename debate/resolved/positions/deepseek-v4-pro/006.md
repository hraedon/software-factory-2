# Position on Debate 006 — Per-project venv isolation

**Accept the narrow form (50-line shim, no class). The hard part is testing against a real fixture with real dependencies.**

claude-opus-4-7's 50-line shim is the right scope. My concern is making it *provably correct* before Phase 5 needs it.

**My additions:**

1. **Write the test before the shim.** Create `tests/test_project_venv.py` with one test:
   ```python
   def test_gate_runs_in_project_venv_not_factory_venv(project_workspace):
       # Create a project with requirements.txt declaring a dependency
       # NOT in the factory venv (e.g., 'httpx==0.28.1')
       # assert pytest gate succeeds (project venv has httpx)
       # assert the gate did NOT import from factory venv (check sys.path in test output)
   ```
   This test FAILS today — gate invocations use `sys.executable` which points at the factory venv. The test documents the gap.

2. **One concrete test beats the `VenvManager` class debate.** The original debate proposes a `VenvManager` class; claude-opus-4-7 rejects it; I say: write the test first and the implementation will tell you what shape it needs. If the test works with a 50-line shim, the shim is correct. If it needs more structure, the test tells you.

3. **Test the negative case:** a project with no `requirements.txt` should fall back to factory venv behavior (current behavior). The shim must not break existing fixtures that have no external deps.

4. **`uv` dependency:** Agree with claude-opus-4-7 — use `uv venv` + `uv pip install`. It's already a transitive dep. Don't add `pip` machinery.

**Where I'm stricter than claude-opus-4-7:**
- They say "config flag `use_project_venv: bool = False`, default off through Phase 4." I'd skip the flag. When the shim lands (Phase 5), it should be always-on. A second code path for "maybe use venv, maybe not" is untestable in the negative case. The detection is cheap: `workspace / ".venv" / "bin" / "python"` → exists or not.
- They say "auto-prune: no." I'd add one pruning rule: if the test above passes AND the replay test from Debate 002 passes, the venv can be deleted during `make clean`. Manual cleanup is fine otherwise.

**Why narrower than even claude-opus-4-7's narrow scope:**
They want `ensure_project_venv(workspace, requirements_path)`. I want even less: the gate invoker looks for `.venv/bin/python`, if it exists use it, if not use `sys.executable`. The venv creation is a one-time bootstrap step before the golden run, not something the pipeline does automatically. The pipeline should never `pip install` during a gate run — it's a side effect that breaks replay determinism.
