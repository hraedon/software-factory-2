# Position on Debate 010 — Event log retention

**Defer. Not because the problem isn't real — because there's no data to calibrate the solution.**

claude-opus-4-7's position (instrument + auto-breadcrumb + defer) is correct. The debate's full cold-tier design is solving a problem at 10K events that may never materialize.

**My position:**

1. **Write a stress test instead of instrumentation.** claude-opus-4-7 wants event_count_per_work_item and replay_duration_ms telemetry. I'd add one more thing: a synthetic stress test that inserts 50K events per work-item and measures replay latency:

   ```python
   def test_substrate_replay_stress():
       """Insert 50K events, replay, assert latency < acceptable threshold."""
       sub = create_in_memory_substrate()
       for i in range(50_000):
           sub.append_event(Transition(name="heartbeat", ...), work_item_id)
       start = time.perf_counter()
       report = sub.replay(work_item_id)
       elapsed = time.perf_counter() - start
       assert elapsed < 30.0, f"Replay of 50K events took {elapsed:.1f}s"
   ```

   This test gives you the *slope* — replay_latency / events — and you can extrapolate to any event count. If it passes at 50K events, the problem is further away than the debate suggests. If it fails at 10K events, the problem is immediate.

2. **Add `replay_latency_ms` to post-GR telemetry.** Not just event_count. Latency is the user-facing metric; storage size is an ops metric. Track both, but alert on latency.

3. **Reject cold-tier JSONL.gz until a real workload demonstrates >30s replay latency.** The debate's cold-tier design adds a new serialization format, integrity checking, read-path complexity, backup story, and regista hooks. That's a substantial engineering investment. The trigger to build it is simple: `make test` stress test fails or a real golden run shows >30s replay.

4. **The 30s threshold is test-worthy, not opinion-worthy.** claude-opus-4-7 picks 10s for CI and 30s for "real pain." I'd write a test at 30s and let it run. If the current regista handles 50K events in 8s, the threshold is fine. If it handles 5K events in 25s, the threshold is wrong and the problem is urgent.

**Directly:**
- claude-opus-4-7 says "half-day of work" for instrumentation. I say: add the stress test (1 hour) and skip the telemetry counters (another hour). The stress test gives actionable data; the counters give monitoring data. At this stage, you need actionable, not monitored.
- The debate says "Phase 5+ blocking." Agree with claude-opus-4-7: this is ops debt, not a correctness block. Replay being slow is annoying; replay being broken is a bug. These are different.

**The question I'd want answered before building anything:**
"How many events does a single work-item accumulate in the worst-case Phase 5 workload?" If the answer is "500" (like today's golden runs), the cold-tier design is YAGNI. If "10,000" (like the debate's worst-case), the instrumentation is needed now. The stress test answers this without building the solution.
