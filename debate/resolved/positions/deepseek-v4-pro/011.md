# Position on Substrate Debate 001 — Backend contract single-source-of-truth

**Defer. The evidence doesn't support the proposed solution.**

The debate identifies a real problem: hand-maintained InMemorySubstrate drifts from Postgres, and the drift is caught late. But the proposed solution (declarative contract + property-based testing) is solving a problem that may already be contained.

**What the data tells me:**
- The debate says "two v2 factory golden-run bugs from InMemory/Postgres divergence" (BC-063)
- Substrate has resolved "ten InMemorySubstrate parity bugs" (BC-045 through BC-058)
- v2 factory has 260 tests, 0 lint errors

That's 12 bugs total, all resolved, in a dual-backend system that supports 260 tests. The question is not "does drift happen?" (it does) — the question is "at what rate, and is it accelerating or decelerating?"

**My position:**

1. **Measure the bug rate before prescribing the cure.** Plot InMemory/Postgres parity bugs per month over the last 6 months. If the rate is flat or declining, the existing process (manual fix + improve conformance test) is working. If it's accelerating, the structural fix is warranted. Without this data, you're prescribing chemotherapy for a headache.

2. **Property-based testing is the right first step, not the contract.** Run `hypothesis`-style randomized API call sequences against both backends for 1 month. Count the divergences found. If `hypothesis` finds 10+ new divergences not caught by existing tests, the contract is justified. If it finds 0–1, the existing conformance tests are adequate and the contract is over-engineering.

3. **The contract adds complexity, not reduces it.** A third source of truth (contract) that sits between two backends creates a new failure mode: contract/Postgres divergence AND contract/InMemory divergence. The debate positions the contract as "the one thing the principal reviews" — but the principal now reviews 3 artifacts (contract, contract-tests, contract-backend-mapping) instead of 2 (InMemory tests, Postgres tests).

4. **Why I disagree with the debate's framing:**
   - "A human adding a new transition rule edits exactly one file" — the contract. But what about performance? Postgres' `SELECT FOR UPDATE` locking has no equivalent in a Python dataclass contract. Someone has to write the Postgres-specific locking logic SOMEWHERE, and that somewhere is now "the mapping layer" which is a new thing to maintain.
   - "The contract file is readable without Python expertise" — a YAML file describing SQL locking semantics is not readable by anyone without database expertise. The principal (systems architect, per AGENTS.md) would need to understand locking semantics to review it.

**Concrete alternative:**
1. Add `hypothesis`-based property testing to CI now (1 day)
2. Run for 1 month; collect bug rate data
3. If hypothesis finds divergences AND bug rate is accelerating → build contract
4. If hypothesis finds no divergences AND bug rate is steady → add more conformance tests, skip contract

**The key question:** Is the InMemory/Postgres drift problem *solved* or *suppressed*? The existing bugs were fixed, but were they fixed structurally (better conformance tests prevent recurrence) or manually (each bug patched individually)? If structurally, no contract needed. If manually, contract may help — but property-based testing helps more.
