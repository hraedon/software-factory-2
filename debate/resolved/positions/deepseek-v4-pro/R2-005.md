# Position on R2-005 — Operator UX & async interrupts

**Accept the minimal notification hook. But a notification that says "something is blocked" with no response path is half the solution. Add a substrate-level approve/reject command.**

claude says ~30 lines: notification_hook + one webhook adapter. Agree, that's the right size. My addition: the notification MUST include an actionable command the operator can run to unblock.

**The missing half:**

The debate (and claude's recommendation) focus on *alerting* — the operator gets a Slack message or webhook POST saying "work-item X escalated." But then what? The operator opens a terminal, runs `substrate transition --work-item <uuid> --to <state>`, and hopes they typed the UUID correctly. That's not operator UX — that's developer UX with extra steps.

**What I'd add:**

1. **The notification payload includes a command.** Each escalation notification carries a field like:
   ```json
   {
     "event": "escalation",
     "work_item_id": "abc-123",
     "reason": "cannot_proceed_seam",
     "action": "substrate escalate resolve abc-123 --accept",
     "action_reject": "substrate escalate resolve abc-123 --reject"
   }
   ```
   The operator copies the `action` string and pastes it into their terminal. No UUID typing, no remembering transition names.

2. **Substrate adds a single new CLI command:** `substrate escalate resolve <work_item_id> --accept|--reject [--reason "..."]`. Accept → transitions to a new state (or back to the role that can fix it). Reject → dead-letter. This is ~20 lines of substrate code + one transition in the workflow YAML.

3. **Test the round trip.** `test_escalation_notification_round_trip()`:
   - Simulate escalation event
   - Assert notification payload contains actionable command
   - Run the command (via mock or integration)
   - Assert work-item state changed

**Why this differs from the debate:**
- The debate says "notification bus + adapter framework for Slack/Discord/Email." That's infrastructure for infrastructure's sake.
- claude says "webhook/Slack event sink." That's the right minimal approach but misses the response path.
- I say: the notification is worthless without the response path. Ship them together.

**On the timing:** claude says Phase 4. I agree — Phase 2–3 golden runs don't accumulate enough escalations to make manual polling painful. By Phase 4, with multi-channel jury gates that can disagree, escalations will be frequent enough that polling becomes infuriating.

**What I'd actually ship:**
1. `notification.py` — ~30 lines: detects escalation events in scheduler, POSTs to webhook URL with structured payload
2. `substrate escalate resolve` — ~20 lines in substrate CLI
3. `workflow transition: escalate_resolve` — ~5 lines in phase4.yaml
4. `test_escalation_notification_round_trip.py` — ~30 lines
5. `FactoryConfig.notification_webhook_url: str | None` — default None (disabled)
