# Position on Debate 012 — Attempt-level latency tracking

**Accept. The spec requires it, the implementation lacks it, and Phase 3 needs it.**

Spec §7 explicitly lists "mean wall-clock" as part of the telemetry report. The current implementation produces only pass rates. GR004 and GR005 show a 68% wall-clock difference (31 min vs 52 min) that is invisible in the telemetry output. Fleet placement on pass rate alone may select a channel that is 40% slower for a 7-point pass rate improvement — a tradeoff the principal should evaluate with full data.

**The design is right:** record invocation start/end times in runner.py, compute duration in telemetry, add a duration column to the report. ~30 lines. The `per_channel_timeout` config option is a natural extension that the data enables.

**Timing:** Build alongside BC-068 fix and Debate 011 (prompt versioning). All three are telemetry data-quality improvements that should land before Phase 3 fleet runs. One session for all three.

**Why this matters for the spec's implementer slot:** The spec §5 table assigns the implementer role to K2 (Tier B, "slot-filling, bulk") with GLM and DeepSeek as fallbacks. But the spec also says "role-to-channel binding is configuration, updated based on telemetry." If K2 passes 80% in 15 minutes and Claude passes 90% in 45 minutes, the implementer slot's optimal binding depends on the principal's time/quality tradeoff — and the principal can't make that tradeoff without the latency data.

**One risk to flag:** latency varies by spec complexity. A trivial spec takes 10s on any channel; a complex spec exposes the channel's real speed. Consider normalizing latency by spec complexity (e.g., AC count or spec text length) in a future iteration. For now, raw mean/median per (role, channel) is sufficient.
