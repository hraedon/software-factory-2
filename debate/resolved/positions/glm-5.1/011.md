# Position on Debate 011 — Prompt versioning in telemetry

**Accept and build alongside BC-068 fix. Both are telemetry data-quality prerequisites for Phase 3.**

The telemetry report compares channels to inform fleet placement. But if the prompt template changes between runs, the comparison confounds channel quality with prompt quality. BC-039 updated the implementer prompt between golden runs. The 7-point pass rate difference between GR004 and GR005 may be partially due to the prompt change, not the channel. Without controlling for this variable, Phase 3 fleet placement is building on a confounded experiment.

**Why this is the same class of problem as BC-068:** BC-068 is about the telemetry data being *wrong* (unknown gate names, incorrect pass rates). This is about the telemetry data being *misleading* (correct pass rates, but the comparison is confounded). Both produce incorrect fleet placement decisions. Both should be fixed before Phase 3.

**The design is right:** prompt template hash (SHA-256 of the template file content) in `actor_metadata`, grouped in telemetry. Not a semantic version — automatic, tamper-evident, zero maintenance. The existing `context_hash` is too broad (includes retry context); a template-only hash is the correct granularity.

**Cost:** ~20 lines. Pair with the BC-068 telemetry fix since both touch `telemetry.py` and `gate_process.py`. One session for both.

**One refinement:** the "confounding warning" when a (role, channel) group has multiple hashes is good for Phase 2 (few runs, manual review). For Phase 3 (many runs, automated placement), the telemetry grouping should be `(role, channel, prompt_template_hash)` — meaning the same channel with different prompts is treated as different data points. This prevents automated placement from comparing across prompt changes silently.
