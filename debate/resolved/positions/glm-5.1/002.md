# Position on Debate 002 — Telemetry data quality (BC-068)

**Accept as a hard block on Phase 3. Fix in the next session.**

Phase 3's entire purpose is fleet integration informed by per-(role, channel, gate) data. Spec §5 is unambiguous: *"Per-role per-channel telemetry drives model placement... updated based on data, not vibes."* When the gate dimension reads `unknown` and the first-attempt-pass dimension reads 0% on successful runs, the placement table is not noisy — it is *inverted*. A channel that passes 80% of implementations appears as 0%. Adding K2/GLM/DeepSeek/Gemini channels on top of this foundation produces 5× the data corruption with no compensating signal.

The four-step fix in the debate is correct. Two refinements:

1. **The replay fixture is the keystone.** The unit tests pass because they use synthetic event shapes that don't match real substrate event shapes from golden runs. This is testing the mock, not the system. Extract a small anonymized event subset from GR004/GR005 (strip artifact paths, hash actor IDs, keep transition names + actor_metadata + payload shape). Assert: zero `"unknown"` gate names, non-zero first-attempt rate, exact gate-pass count matches the recorded run. This fixture is the canary for future event-shape drift.

2. **The root cause is two things, not one.** The debate identifies gate_name extraction failure, but the 0% first-attempt rate suggests the pairing logic itself is also wrong — it may not be correctly correlating first attempts with their gate outcomes. Fix both: (a) make gate events self-describing via actor_metadata, (b) validate the submit→gate pairing logic against the replay fixture.

**Why hard-block, not parallel:** if the fix lands mid-Phase 3, every channel comparison run before the fix is invalid data. Phase 3's channel comparison is the most expensive empirical exercise in the project plan. Doing it once correctly is cheaper than doing it twice — once on corrupt data, once on clean data.

**Connection to Debate 009:** the structural fix for producer/consumer schema drift is Debate 009's consumer-level schema pilot. If session budget allows, land 009 alongside BC-068 so the fix has a regression guard. If not, BC-068 is the priority.
