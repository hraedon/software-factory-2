# Position on Debate 010 — Unbounded event log growth

**Defer. Add instrumentation. Auto-file breadcrumb when thresholds are breached.**

The debate correctly identifies the trajectory: append-only event logs grow linearly, and 30-day missions with daily retry loops could produce 10K+ events per work-item. But the current state is ~500 events per golden run (15 work-items × ~33 events each). This is nowhere near the thresholds the debate proposes (replay >30s, events >10K per work-item).

**What to do now (instrumentation, not architecture):**

1. Add `replay_duration_ms` to the telemetry reporter. Track it per golden run. If it trends upward, the data exists to decide.
2. Add `event_count_per_work_item` to the telemetry reporter. Flag items with >100 events.
3. After each golden run, the runbook checks these metrics. If either threshold is breached, auto-file a breadcrumb.

This is ~20 lines of code in `telemetry.py` and adds exactly zero architectural complexity.

**Why defer the hot/cold tiering:**

The proposed design (hot Postgres + cold JSONL.gz files, replay reads both) is well-designed. It's also:

- A new storage backend alongside Postgres
- A new read path in regista's `read_events()` and `replay()`
- A compression dependency (gzip is stdlib, but the archival format needs versioning, integrity checks, manifest files)
- A nightly job or manual trigger for compaction

All of this is correct infrastructure for when event counts reach 10K+. But building it now is solving a problem that doesn't exist. The simpler compaction (collapsing heartbeat and poll_hooks events within Postgres) is a better first step if thresholds are ever breached.

**The debate's own "next step" agrees:** measure first. The four steps are: (1) add telemetry metrics, (2) run stress test, (3) set thresholds, (4) keep debate open. That's the right sequencing. Don't jump from measurement to architecture in one step.

**One concrete number to track:** the debate estimates 10K events per work-item for 30-day missions. Current golden runs produce ~33 events per work-item. The growth rate from Phase 2 → Phase 3 → Phase 5 is the key metric. If Phase 3 (multi-channel, more retries) doubles it to ~66, we're still 150× below the threshold. If Phase 5 (real workloads, longer retry chains, daily checkpointing) pushes it to 1000, the architecture conversation starts.
