# Position on Debate R2-002 — Bidirectional Spec Mutability

**Defer the formal amendment mechanism to Phase 5+. Improve the existing fast-path for spec impossibility detection now.**

This is the most architecturally interesting R2 item. The debate asks: what happens when the *spec itself* is impossible, not just the interface? The current architecture handles interface-level revision (Stage 7 jury disagreement → Stage 2 interface architect), but the implementer discovering that the spec references a deprecated API has no fast path to flag this.

**Why the problem is real but the solution is premature:**

1. **Phase 2-4 specs are principal-authored.** The principal is a systems architect who wrote the spec intentionally. "Spec is impossible" in this regime means the principal made an error — and the current 3-attempt → `cannot_proceed` → principal escalation path handles this correctly (if slowly).

2. **Phase 5+ specs may be Socratic-authored.** The spec §4 Stage 0 describes "Socratic elaboration (existing /spec skill, lifted from socratic-specification)." If the spec is generated through an interactive elicitation process rather than hand-written, the probability of impossible specs increases. At that point, a formal `propose_spec_amendment` transition is load-bearing.

3. **The proposed design has an authority problem.** Who decides the spec is invalid? The implementer is a "filling-in role" (spec §3.6: "bounded by interface, cannot change signatures"). The implementer should NOT have authority to declare the spec wrong — it should route through the interface architect, who is better positioned to assess feasibility. But the interface architect is also bounded by the spec. The only role with authority to amend the spec is the principal. So `spec_invalid` always routes to principal escalation regardless — which is what `cannot_proceed` already does.

**What to improve now (without a new transition):**

The current failure routing takes 3 attempts before escalation. If the implementer detects an impossible spec on attempt 1, it still has to fail 2 more times before the principal sees it. This is wasteful. Two improvements:

1. **Add `cannot_proceed` as a valid implementer output.** Currently the implementer can return structured `{"status": "cannot_proceed", "reason": ...}`. Extend this to include a `spec_impossibility` diagnostic kind that the router recognizes and routes directly to principal escalation (skipping the retry loop). This is a 10-line change in `router.py`.

2. **Include spec-reasoning in the implementer prompt.** The implementer prompt (45 lines) doesn't tell the implementer it CAN flag spec impossibility. Add a sentence: "If the acceptance criteria reference something impossible (deprecated API, contradictory requirements), return `cannot_proceed` with reason `spec_impossibility`." This is a 1-line prompt change.

**Why not the full `propose_spec_amendment` transition:**

- It requires a human-in-the-loop approval mechanism for spec changes. The principal must approve amendments. Currently the principal's only interaction point is Stage 10 (outcome review). Adding a mid-pipeline human gate contradicts the "no human code review" principle (spec §1: "the architecture must not require human code review as a gate — that gate would always be rubber-stamped or skipped").
- It creates a new event type, new routing rules, and new state machine transitions in the workflow YAML. All before the problem has been demonstrated in a real run.
- The fast-path improvement (direct escalation on `spec_impossibility`) provides 80% of the value at 5% of the cost.

**When to build the full mechanism:** After Phase 5 encounters a real case of spec impossibility that the fast-path handles clumsily. At that point, the concrete requirements will be clear and the design will be grounded in experience, not speculation.
