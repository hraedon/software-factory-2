# Position on Debate R2-004 — Security and Supply Chain Gates

**Accept `bandit` now. Accept `pip-audit` pre-Phase 5. Reject `trufflehog`/`semgrep`.**

The debate raises a valid concern: autonomous agents writing code for days will introduce vulnerabilities. But the proposed solution mixes gates that provide high signal with gates that don't match the deployment model.

**Accept now — `bandit`:**

`bandit` scans Python source for common security issues (hardcoded passwords, eval() usage, shell injection, assert-based security). It runs against source code directly, requires no dependencies to be installed, and has low false-positive rates. Add as a mechanical gate in `evaluate_implementation()` — same pattern as ruff. Trivial to add (~20 lines). Even Phase 2-4 fixtures benefit: catching a hardcoded test credential in generated code is worthwhile.

**Accept pre-Phase 5 — `pip-audit`:**

`pip-audit` checks `requirements.txt` against known CVE databases. Requires the per-project venv (Debate 006) to be in place. Phase 2-4 fixtures have no `requirements.txt`, so `pip-audit` has nothing to scan. Gate Phase 5 on it, alongside the venv helper.

**Reject — `trufflehog`/`semgrep`:**

- `trufflehog` scans git history for secrets. The factory writes artifacts to workspace directories, not git repositories. There is no git history to scan. The factory would need to initialize a git repo, commit generated code, and then scan — adding complexity with no clear benefit over `bandit` (which catches hardcoded secrets in source).
- `semgrep` is powerful but requires custom rules and produces higher false-positive rates. `bandit` + `ruff` (already in the gate stack) cover the same ground for Python-specific issues. Add `semgrep` only if Phase 5 shows patterns that `bandit` misses.

**Failure routing:** Same as existing mechanical gates — route back to implementer with the security finding and a prompt instruction to fix the specific vulnerability type.
