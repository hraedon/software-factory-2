# Position on Debate 007 — Credential management

**Accept the `credentials.yaml` schema. Reject rotation detection, audit, and per-project isolation for Phase 3.**

Phase 3 cannot proceed without a way to supply API keys to K2, GLM, DeepSeek, and Gemini adapters. But the debate proposes four features (schema, rotation, audit, isolation) when only one is load-bearing: loading a key from a file and injecting it into the channel adapter.

**Phase 3 minimum (~30 lines):**

1. `~/.config/factory/credentials.yaml` with the schema as proposed.
2. `CredentialManager.load(path)` reads the file, returns a dict of `{provider: api_key}`.
3. FactoryConfig gets a `credentials_path: Path | None` field.
4. Channel adapters receive the key via `role_config.api_key` and inject it as an env var or CLI flag.

That's it. No rotation detection (if a key is revoked, the channel fails, the runner retries on a different channel — existing fallback behavior). No audit (the principal can read the YAML directly). No per-project isolation (Phase 3 has one project at a time).

**What to defer:**

- **Rotation detection:** Requires parsing provider-specific HTTP 401/403 response bodies for K2, GLM, DeepSeek, and Gemini. Four different error formats, none documented in the debate. The existing fallback mechanism (channel fails → scheduler reassigns) handles key failures implicitly. Explicit rotation detection is a Phase 5+ feature.
- **Audit with hashed key IDs:** The principal can review `credentials.yaml`. Hashing key IDs adds complexity without adding security — the file is already outside the repo and owner-read-only by convention.
- **Per-project isolation:** Phase 3 runs one project at a time. Per-project keys solve a problem that doesn't exist yet.

**Why not env vars:** The debate is correct that env vars are inferior — they leak to subprocess gates (pytest inherits env) and are invisible to the principal. `credentials.yaml` is the right answer. Just don't over-build the consumer.
