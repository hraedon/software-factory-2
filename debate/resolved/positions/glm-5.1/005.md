# Position on Debate 005 — Mutation testing

**Accept the principle. Build an assertion-counting gate now; add full mutation testing between Phase 3 and Phase 4.**

The test-theater risk is real. Spec §8.9 acknowledges it. Luke's quote ("tests written after implementation don't catch bugs, they confirm decisions") is direct corroboration. But mutation testing is expensive — 10 operators × N functions × pytest per mutant — and the debate underestimates the wall-clock cost.

**Cheaper first step: assertion-counting gate.**

Before investing in AST mutation, add a lightweight gate that counts `assert` statements in collected test files:

1. After `pytest_collect` passes, read the collected test file paths.
2. Parse each file's AST. Count `Assert` nodes.
3. Fail if any test file has zero assertions, or if total assertions < number of test functions.

This catches the most common form of test theater (tests that run but never assert) at near-zero cost (~20 lines of code, <1s per gate run). It doesn't catch tautological assertions (`assert True`) but it catches the vacuous case. BC-038 (pytest collectability) already catches zero-test suites; this extends the same principle.

**Mutation testing timing:** Between Phase 3 fleet completion and Phase 4 jury. This gives:

1. Multi-channel data to calibrate the threshold (different channels may produce different test-quality distributions).
2. The jury can use mutation kill rate as one input among (cross-family review, jury vote, mutation rate).
3. Building before Phase 3 is wasted — the data has nowhere to flow until the jury exists.

**Where I agree with the debate:**

- Custom 10-operator mutator beats `mutmut`/`cosmic-ray`. The proposed operator set (comparison flips, arithmetic flips, boolean flips, guard deletion, branch swaps) is the high-signal set.
- Threshold from empirical data, not intuition. Threshold lives in `FactoryConfig`.
- Cache by implementation hash. Without caching, mutation testing is O(impls × tests × operators) per gate run.

**Where I'd push back:**

The `Replace 0 with 1, "" with "x"` operator class is high-noise. Many correct functions return constants. Drop it from the initial set. Also: the debate doesn't address the wall-clock concern concretely. For 15 implementations × 10 operators × 50-test suite at 2s/pytest = 25 minutes per gate cycle. Parallelize mutants (safe — read-only) or limit operators to functions covered by the test suite's import graph.
