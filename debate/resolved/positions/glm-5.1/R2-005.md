# Position on Debate R2-005 — Operator UX and Async Interrupts

**Accept a webhook-only notification sink, implemented in the factory (not substrate). Defer Slack/Discord/Email adapters and any dashboard.**

The principal's value prop ("approve the plan and go do something else") requires knowing when the pipeline needs attention. Today the principal polls the CLI. The debate proposes an event-driven notification sink, which is the right direction. But the design choices about *where* and *how much* matter.

**Where: factory, not substrate.**

The debate says "build an event-driven notification sink in Substrate." This is wrong. Substrate is the coordination spine — it stores state and dispatches hooks, but it should not own notification logic. Substrate already has hooks that dispatch events. The factory should consume those hooks (as it already does for telemetry) and implement notification as a factory-level concern. Putting notifications in substrate means every substrate consumer gets notification infrastructure whether they want it or not, and substrate takes on a dependency on HTTP client libraries, webhook retry logic, and adapter frameworks.

**What to build (~30 lines in the factory):**

1. Add `notification_webhook_url: str | None = None` to `FactoryConfig`.
2. Add a `notify(event_type, payload)` function that POSTs a JSON payload to the webhook URL.
3. Call `notify()` from the scheduler on two events:
   - `cannot_proceed` (escalation to principal — the only human-in-the-loop event)
   - `mission_budget_exhausted` (from R2-001 circuit breaker)
4. Optionally: `mission_complete` (all items locked or escalated).

That's it. No adapter framework. No Slack SDK. No email templates. A single webhook POST is the universal interface — Slack, Discord, and email all accept webhooks natively.

**Why not the adapter framework:**

The debate proposes "a simple adapter framework for Slack/Discord/Email." An adapter framework is the kind of premature abstraction the spec §3 warns against. Each adapter has different message formatting requirements, rate limits, and authentication. Building three adapters before knowing which one the principal actually uses is wasted effort. A webhook URL is the minimum — the principal can point it at a Slack incoming webhook, a Discord webhook, or a custom endpoint.

**Why not a dashboard:**

A dashboard is a full UI application. The spec §1 says the principal is a systems architect, not a developer. A Postico query against the substrate database, or the existing `factory-report` CLI, serves the same purpose. A dashboard is Phase 6+.

**Pair with R2-001:** The notification hook without the budget breaker has nothing critical to alert on (cannot_proceed events are rare and the principal will discover them eventually). The budget breaker without the notification hook is silent. Land them together.
