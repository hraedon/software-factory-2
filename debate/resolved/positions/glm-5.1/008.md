# Position on Debate 008 — Adversarial fixture before Phase 2 close

**Accept. Run an adversarial fixture before Phase 2 closes. Target 3-of-5 characteristics (multi-module, stateful, error taxonomy), not 5-of-5.**

The 87-93% pass rates on curated fixtures are informative but not predictive. The fixtures are self-contained, single-module, dependency-free libraries — the easiest regime for any pipeline. Without an adversarial datapoint, Phase 3 fleet tuning operates on a vanity metric.

**Why 3-of-5, not 5-of-5:**

The debate lists five adversarial characteristics: multi-module, stateful, error taxonomy, UI, AC ambiguity. Running all five in one fixture conflates two questions:

1. *Does the pipeline handle non-trivial specs?* (multi-module + stateful + error taxonomy)
2. *Does the pipeline handle ambiguous specs and UI targets?* (AC ambiguity + UI)

Question 1 is answerable now. Question 2 requires infrastructure that doesn't exist yet (behavioral gate for UI, orchestrator clarification loop for ambiguity). Mixing them produces a result that's hard to interpret — did the pipeline fail because of spec complexity or because of missing infrastructure?

**Concrete fixture:** Cert-watch FR-02 (TLS scan + cert extraction) + FR-03 (file upload + parse) as two linked work-items sharing a `Certificate` model. This exercises:

- Cross-work-item module imports
- Real I/O at gate time (sockets, filesystem)
- Non-trivial error taxonomy (bad host, refused connection, expired chain, malformed PEM)
- Stateful contract (chain extraction depends on TLS handshake state)
- v1 priors across 11 attempts for comparison

**Pass criteria — three meaningful outcomes, not pass/fail:**

| Result | Interpretation | Action |
|---|---|---|
| ≥70% impl pass | Curated fixtures generalize | Phase 2 closes; proceed to Phase 3 |
| 40-70% impl pass | Partial generalization; gap is identifiable | Close Phase 2 but file gap as Phase 3 monitoring item |
| <40% impl pass | Curated fixtures don't generalize | Pause Phase 3; root-cause before adding channels |

**Where I agree with claude-opus-4-7's cert-watch suggestion:** the cert-watch domain is ideal — real I/O, real error conditions, v1 priors, and the right size for a single adversarial run. Running it as GR006a (adversarial) and deferring the full cert-watch (GR006b with UI + AC ambiguity) to Phase 5 pre-flight is the right sequencing.

**One risk the debate undersells:** cert-watch FR-02 requires network access (TLS connections to real hosts). This is a new dependency for the gate environment. The fixture may need a mock TLS server or a well-known stable target. Solve this at fixture-design time, not during the golden run.
