# Position on Debate R2-003 — Database Migration Strategy

**Accept as a mechanical gate concern, not a new pipeline stage or sub-agent. Gate Phase 5 cert-watch on it.**

The debate is correct that LLMs are bad at writing sequential, state-preserving database migrations. The proposed solution (declarative schema + deterministic tooling + validation gate) is the right approach. But the framing as a "specialized architectural pattern or sub-agent" over-scopes what should be a mechanical gate constraint.

**What to build:**

1. **Interface architect prompt includes data persistence section.** When the spec requires database interaction, the interface architect's output should specify: "Use SQLAlchemy models + Alembic for migrations." This is a prompt constraint, not a pipeline change.

2. **Add `alembic_upgrade_head` as a mechanical gate.** After implementation, run `alembic upgrade head` against a test database. If it fails (migration doesn't apply cleanly), route back to implementer with the Alembic error output. This is a standard gate — same pattern as mypy/pytest/ruff.

3. **No new sub-agent.** The implementer produces the migration as part of the implementation. The gate validates it. If the migration is wrong, the gate fails and the implementer retries with the error context. This is the existing failure-routing pattern.

**Timing:** Pre-Phase 5, not before. Phase 2-4 fixtures don't have databases. The cert-watch adversarial fixture (GR006a) uses filesystem I/O, not database I/O. Database migrations become load-bearing only when Phase 5 targets a stateful application.

**Why Alembic specifically:** `alembic revision --autogenerate` produces deterministic diffs from SQLAlchemy models. The implementer writes models; Alembic generates the migration. This reduces the LLM's migration-writing burden to "write correct models" (which it can do) rather than "write correct SQL migrations" (which it often can't).
