# Position on Debate R2-001 — Infinite Spend Circuit Breaker

**Accept the principle, reframe from "financial spend" to "wall-clock budget." Build before Phase 3.**

The concern is valid but the framing is wrong. Spec §2 states: *"Subscription-flat-rate cost model rewards aggressive gating. All channels are flat-rate; the budget is wall-clock time and rate limits, not tokens."* There is no per-token cost. The financial risk is bounded by subscription fees. The real risk is **wall-clock time waste**: a stuck retry loop burning hours of pipeline time against rate limits, consuming the principal's patience without producing output.

**What already exists:**

- `attempt_threshold: int = 3` in `FactoryConfig` — caps per-work-item retries
- `cannot_proceed` transition after attempt exhaustion — halts the stuck item
- `gate_escalation` routing (BC-037) — terminates items that can't recover

These are per-item circuit breakers. What's missing is a **global** circuit breaker: a cap on total pipeline runtime that halts the entire mission when exceeded.

**What to build (~40 lines):**

1. Add `max_mission_wall_clock_seconds: int | None = None` to `FactoryConfig`. `None` means no global cap (current behavior, backward compatible).
2. Record `mission_start_time` when the runner begins processing.
3. Before each new claim, check: `now - mission_start_time > max_mission_wall_clock_seconds`. If exceeded, force-transition all active items to `cannot_proceed` with reason `mission_budget_exhausted` and exit.
4. Pair with R2-005 notification hook so the principal is alerted when the breaker trips.

**What NOT to build:**

- Token usage tracking — channels are flat-rate, token counts are irrelevant to cost
- Per-provider cost estimation tables — adds complexity with no signal
- `max_mission_budget` as a dollar amount — the cost model doesn't support it

**Why this matters for Phase 3:** Multi-channel runs with fallback chains (Claude → GLM → K2) can compound wall-clock. If the primary channel is silently degraded (slow responses, rate-limited), the pipeline may spend hours cycling through fallbacks without the principal knowing. A global wall-clock cap is the backstop.

**Existing precedent:** v1 had a "Global Budget Breaker." The lesson is the pattern, not the implementation — v1 tracked tokens because v1 paid per token. v2 tracks wall-clock because v2 pays per subscription.
