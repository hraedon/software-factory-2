# Position on Debate R2-006 — Dead Code and Refactoring Lifecycle

**Accept as a trivial extension of existing audit. Reject the "consolidation agent" / periodic refactoring stage.**

The factory already has dead-code detection: `make audit` runs `vulture` (BC-057), integrated into CI via `make check`. The concern about "sludge" accumulation over 16-day missions applies to v1 (which ran continuously) but not to v2, which runs discrete golden runs. Each golden run starts from a clean workspace — generated artifacts are per-run, not cumulative. The factory code itself is version-controlled and audited in CI.

**What to add (10 minutes):**

Run `make audit` at the end of every golden run. If vulture reports any findings, auto-file a breadcrumb. This is a runbook addition, not a code change.

**What NOT to build:**

- A "Refactoring/Cleanup" pipeline stage — generated artifacts are per-work-item and per-attempt. There is no accumulation to clean up within a run.
- A "consolidation agent" — this is a new role that writes code, which contradicts the spec's principle of bounded, filling-in roles (spec §3.6).
- Behavioral gates after cleanup — cleanup doesn't happen, so there's nothing to verify.

**When this becomes real:** If Phase 5+ introduces long-running missions (16+ days) where generated code accumulates across iterations. At that point, a cleanup gate that runs `ruff` + `vulture` on the generated codebase and routes findings to the implementer is reasonable. But Phase 2-4 does not have this problem.
