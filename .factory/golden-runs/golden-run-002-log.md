## Summary

The first multi-stage golden run failed because the implementation gate's subprocess-based checks (`_run_pytest`, `_run_mypy`) could not resolve cross-work-item imports. Test suites generated by the `test_author` role import from `interface` (the canonical module name for the locked `.pyi` contract), but the implementation artifact lives in a different workspace directory under the filename `artifact.py`. Every implementation attempt failed with `ImportError` on pytest collection, triggering an infinite retry loop that consumed the entire Claude budget without producing a single locked implementation.

## Findings

### Finding 1 (primary): Cross-work-item module resolution in subprocess gates

**Severity:** Critical — blocks all Phase 2 execution.

**Root cause:** `_run_pytest` and `_run_mypy` in `gate.py` operated on files in their original workspace directories without setting up the Python import path. Test suites import `from interface import safe_compute, IntResult, ...` because the `test_author` role prompt instructs writing tests against the locked interface, and Claude naturally uses the module name `interface` for the `.pyi` content. But the interface `.pyi` and the implementation `.py` live in separate work-item directories:

```
/tmp/sf2-golden-002/
  <interface_spec_id>/attempt-0001/artifact.pyi   # the locked interface
  <test_suite_id>/attempt-0001/artifact.py        # the test suite
  <implementation_id>/attempt-0001/artifact.py    # the implementation
```

When pytest runs, `from interface import ...` resolves to neither the `.pyi` (wrong directory, and Python doesn't import `.pyi` at runtime anyway) nor the implementation (named `artifact.py`, not `interface.py`).

**Why the tests didn't catch this:** The existing test `test_gate_implementation_subprocess.py::test_pytest_pass_passes_gate` creates `compute.py` and `test_compute.py` in the same `tmp_path` directory with matching import names. This doesn't exercise the cross-directory, cross-work-item import pattern that the real pipeline uses.

**Fix applied:** Both `_run_pytest` and `_run_mypy` now create isolated temp directories, copy artifacts with correct module names, and run subprocesses from there:

- `_run_pytest`: copies implementation as its original filename AND as `interface.py`, copies test suite, runs pytest from temp dir.
- `_run_mypy`: copies implementation as `interface.py` and interface stub as `interface.pyi`, runs mypy from temp dir.

This ensures the test suite's `from interface import ...` resolves to the implementation at runtime, while mypy cross-checks against the `.pyi` stub for type conformance.

### Finding 2 (secondary): Escalation routing is a no-op for non-interface_spec types

**Severity:** High — allows infinite retry loops that waste model budget.

**Root cause:** When the router's escalation logic triggers (same diagnostic kind exceeds `attempt_threshold`), it produces a `cannot_proceed_seam` route with `target_role="interface_architect"`. But the implementation work item goes back to state `new`, and the worker determines the role from `type_to_role` (implementation → implementer), not from the diagnostic's `target_role`. The implementer re-claims the item, produces another failing implementation, and the cycle repeats indefinitely.

Evidence from the run: items with escalation diagnostics (`cannot_proceed_seam`, `escalated_from_kind=impl_pytest`) continued cycling for up to 80 attempts after escalation fired. The escalation sets a flag that nobody reads.

**Impact:** An implementation item that genuinely cannot pass the gate will cycle until the Claude budget is exhausted, instead of surfacing to the principal after 3 attempts.

**Required fix:** Escalation for non-interface_spec work items must either:
(a) Transition the item to `cannot_proceed` (terminal state), preserving the escalation diagnostics for the principal.
(b) Create a new `interface_spec` work item linked to the failing implementation, with the escalation context as its spec section.
(c) Change the work item's type (not supported by current substrate API).

Option (a) is simplest and sufficient for Phase 2. The principal sees dead-lettered implementations with full failure context.

**Breadcrumb:** BC-037 (new, to be filed).
