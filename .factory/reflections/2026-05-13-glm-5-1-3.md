## On the project

The project is in strong shape for Phase 4 entry. Phase 3 exit criteria are all met, the inner gate is delivering 74% first-attempt pass rates, and the codebase is well-factored with 597 tests. The jury/review skeleton has been in place since BC-132 but has never been exercised end-to-end — that's the obvious next step.

What feels right: the `_invoke_juror` extraction in jury.py makes parallelization trivial — each juror is a pure function of channel + prompt + timeout. The try/except in `_process_jury_work_item` follows the same pattern already established for worker invocations (log, emit channel_fail, continue). The context.py guard turns a silent failure mode (empty template = model produces garbage) into a loud crash.

What I'm less confident about: the `ThreadPoolExecutor` in `run_jury()` works correctly with mock channels in tests, but real channels (opencode, claude) are subprocess-based. Python's GIL won't matter since the channels are I/O-bound subprocess calls, but error propagation from thread to main in the concurrent model relies on `future.result()` which re-raises. Should be fine, but worth watching in the first real jury golden run.
