# Session Reflection — 2026-05-14

**Work summary:** Completed the Gemini capability-probe matrix (Flash + Pro), validated Node 24 PATH fix for Gemini CLI, resolved BC-136 channel failover with per-role fallback config, and updated Phase 4 status. 650 tests pass, 0 lint errors.

## On the project

The pipeline is now genuinely multi-model. Six channel families are validated (Claude, K2-Fireworks, K2-Ollama, GLM-z.ai, GLM-Ollama, DeepSeek-Ollama, Gemini). The channel adapter abstraction has proven its worth: adding Gemini failover took ~30 lines of runner.py changes and 13 focused tests. The spec's §10 gate budget (15 gates for Phase 4) is respected — no new mechanical gates were added; the failover is a runner-level routing concern.

The remaining friction is model ID volatility. `gemini-2.5-pro` is sometimes unavailable (429 "No capacity"), and `gemini-3.1-pro` doesn't exist as a model string. The CLI doesn't surface a reliable model list. This is a harness-shaped problem, not a pipeline-shaped one, but it means Gemini remains probationary despite passing the probe.

## On the work done

**What went well:**
- BC-136 implementation is clean and minimally intrusive. The `_should_failover()` helper centralizes the trigger logic; the fallback is injected at exactly two points (primary invocation and inner-gate retry). The jury fallback with `_fb` channel key preserves telemetry identity without proliferating juror slots.
- Gemini Pro's capability-probe results are strong. It flagged all 5 planted defects in the flawed interface, produced a correct `consume -> float | None` signature, and completed implementer in 76s (vs Flash's 161s). The principal was right that Flash was unfair to Gemini.

**What I'm unsure about:**
- The failover telemetry surface. `ChannelFailPayload.diagnostics` now carries `fallback_channel` and `fallback_model` when failover is attempted. This is sufficient for manual debugging, but telemetry.py doesn't yet aggregate failover rates. If a provider is chronically flaky, the principal won't see it in the report unless they inspect individual channel_fail events.
- No golden-run validation of failover. The unit tests mock channels, which proves the wiring is correct, but a real provider outage is a timing/race condition that mocks don't exercise. The first time failover saves a run, we'll only know retroactively.
- Gemini CLI still prints `Warning: True color (24-bit) support not detected` and `YOLO mode is enabled` to stderr on every invocation. This is harmless but noisy. The `gemini_channel.py` adapter doesn't filter stderr, so these warnings appear in `raw_stderr.txt` for every Gemini work item.

**What was awkward:**
- `capability_probe_gemini.py` is a one-off script, not integrated into the runner or `make test`. If the principal wants to re-run this monthly, it'll need babysitting. Same complaint as the previous session's probe runner.
- The Gemini model name guessing game (`gemini-2.5-pro` works sometimes, `gemini-2.5-pro-exp-03-25` doesn't, `gemini-3.1-pro` doesn't exist). There should be a canonical model ID list somewhere, but I couldn't find it.
