## On the project

The principal is systematically using v1 as a source of "what not to do" and v2 is the better for it. The codebase is disciplined: constants centralized, config-driven, substrate-spined. But the principal's observation is the sharpest one: **v2 has all the ingredients to repeat v1's collapse and none of the structural defenses to prevent it.** The telemetry is good (BC-128, BC-126), the prompts are iterated (BC-122), the gates are compositional (RFC-005) — but there is no complexity budget, no stop condition, no policy that says "after N recurrences, the response is upstream, not downstream."

That's what this session fixed. The spec amendment is the structural defense. The gate-budget test makes it enforceable. The RFCs provide the Phase 5 prerequisites v1 had and v2 lacked.

What still feels fragile: the Phase 5 description in spec.md was "pick a small LoB tool" with zero infrastructure prerequisites. That's now corrected in the spec, but the gap was large enough that it should have been caught earlier. The factory is good at measuring its own output (telemetry) but weak at measuring its own operational footprint (disk, logs, cleanup).

## On the work done

The spec amendment is the most important piece. It doesn't just add a number (12 gates for Phase 3); it adds a **5-step response hierarchy** that makes the default response to a new bug class a prompt/role/spec change, not a new gate. This inverts the v1 incentive structure where adding a gate was the path of least resistance.

The RFCs are conservative in scope. Each one explicitly says "Phase 5 MVP" vs "future phase" and lists what is out of scope. This respects the spec's phasing discipline.

The `test_gate_budget.py` test is a cheap but high-leverage enforcement mechanism. It counts `evaluate_*` and `pre_gate_*` entry points and fails the test suite if the budget is exceeded. The error message quotes the spec §10 rationale, so the next agent who sees the failure knows the policy, not just the number.

What was awkward: counting gates is slightly heuristic (`evaluate_*` and `pre_gate_*` functions). A future refactor could split a single function into multiple entry points and accidentally trip the budget. The test comment documents this — it's a mechanical count, not a semantic one. If the test fails, the fix is either to justify the gate per spec or to refactor the count logic, not to raise the limit blindly.

## Gaps to flag

- **`breadcrumbs/README.md`**: The active bugs table still has only BC-120. With 5 new RFCs and 14 existing ones, the gap coverage is good but the README index will need periodic maintenance. The principal should review the RFC list and decide which to schedule for Phase 5.
- **`spec.md §10`**: The gate budget table is hardcoded. If a future phase needs a different budget, it requires a spec amendment. That's correct per spec authority, but it means the test (`test_gate_budget.py`) will need updating too. Keep them in sync.
- **`tests/test_gate_budget.py`**: The gate count is heuristic. If `pre_gate.py` gains a helper function named `pre_gate_something` that is not a top-level gate entry point, the count will be wrong. A more robust approach would be an explicit registry (e.g., a `GATE_REGISTRY` dict in `constants.py`), but that adds ceremony. The heuristic is fine for now; revisit if it produces false positives.
- **`RFC-017`**: The `.orig` and `.corrupt/` cleanup targets were added to the RFC text but there's no code implementing them yet. In the next golden run, `.orig` files will continue accumulating until RFC-017 is implemented.
- **`RFC-019`**: The bundle gate (`evaluate_bundle`) counts as 1 gate toward the Phase 5 budget of 18. The current count (8) + bundle (1) + potential Phase 4 jury gates (3) = 12, leaving 6 gates of headroom for Phase 5 integration/end-to-end verification. That's tight but workable. If Phase 5 needs more, the spec amendment process must be used.
