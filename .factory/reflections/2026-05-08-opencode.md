## On the project

SF2 is in good shape for where it is in Phase 2. The 7-module decomposition has held up — Wave 6's tests were straightforward to write because `process_work_item`, `process_gate_item`, and `_ensure_downstream_item` compose cleanly. No test needed to mock internal state or bypass abstractions. The test helpers (`_run_worker_stage`, `_run_gate`, `_create_downstream`) are thin wrappers around production functions, which is exactly what you want — each test exercises real code paths, not a parallel test-only implementation.

The InMemorySubstrate migration (Session 7) was a high-impact move. The audit confirmed zero divergence across all 7 areas SF2 cares about — transitions, role enforcement, ref validation, link types, escalation, claims, and query filtering. This is no longer a liability. The test pyramid is well-layered: real-Postgres roundtrip tests cover substrate conformance, InMemory tests cover pipeline logic.

One minor friction: the router's `_ESCALATABLE_KINDS` set is defined in `router.py` but the escalation logic lives in both the router (for routing) and the substrate (for `needs_review`). These are coordinated by configuration (both read `attempt_threshold` from the workflow), not by shared state, which is correct but subtle. An agent unfamiliar with the split might try to implement escalation entirely in the router.

## On the work done

The integration tests came together cleanly. The `_IntegrationChannel` and `_IdempotencyChannel` are deliberately separate classes — integration tests needed configurable AC IDs (for the three-distinct-specs test), while idempotency tests needed the `_resume_and_gate` helper. Combining them into a single test double would have been wrong; they test different dimensions.

The escalation test was the only one that required understanding the router's internal dispatch table. The fix (changing `diagnostic_kind` from `syntax` to `impl_mypy`) was correct — `syntax` isn't in `_ESCALATABLE_KINDS` because syntax errors are deterministic gate failures that won't improve on worker retry. But this isn't obvious from the test alone. A comment in `_ESCALATABLE_KINDS` explaining *why* those particular kinds are escalatable would help.

The idempotency tests are necessarily verbose — each "resume from crash" requires setting up the prior stages of the pipeline, which means duplicating the stage-driver code. The `_resume_and_gate` helper mitigated this somewhat, but `test_mid_pipeline_crash_at_each_stage` is still 50+ lines. This is acceptable for a test that exercises a load-bearing invariant, but it's the kind of test another agent might be tempted to refactor into a shared helper that obscures what's being asserted.

## Gaps to flag

- **`_ESCALATABLE_KINDS` is undocumented.** `router.py:148-156` — the set distinguishes "worker-retry might fix this" kinds from "deterministic failure" kinds, but there's no comment explaining the taxonomy. The escalation test I wrote relied on trial-and-error to discover that `syntax` isn't escalatable. A one-line comment would save the next agent the same debugging.

- **No test exercises the escalatable path end-to-end against a real worker retry.** The escalation test (`test_cross_stage_escalation_after_attempt_threshold`) manually constructs a `GateResult` and calls `route()` directly — it tests the routing logic, not the full loop where a worker actually hits attempt_threshold, escalates, and the interface_architect picks up the `cannot_proceed_seam`. The plan calls this out ("cross-stage escalation: scripted failures at attempts 1, 2, 3 in implementer; assert escalation to interface_architect") — my implementation tests routing, not end-to-end escalation.

- **`test_pipeline_integration.py` doesn't use the real substrate fixture.** All integration tests run against InMemorySubstrate. The plan says "against a real substrate (docker-compose-test Postgres) + MockChannel." The InMemorySubstrate audit confirms this is safe, but a single smoke test against real Postgres would close the loop. The `mock_substrate_v2` fixture removal was correct (it was dead code), but the real-Postgres gap for pipeline integration tests is worth noting.

- **Golden-run-001 fixtures are thin.** Only 12 artifact hashes in `tests/fixtures/golden-run-001/artifacts/`. No replay test validates byte-identical context bundles against them. This was Phase 1's exit criterion but the replay test appears to be a stub — the `test_golden_run.py` file has structural checks but doesn't actually replay recordings.
