## On the work done

Went smoothly. The plan's implementation steps were precise and in the right order. The one wrinkle: `inject_boot_ac` initially checked for `AC_BOOT_ID in spec_text` (the string "AC-BOOT-01"), which matched the bare heading `## AC-BOOT-01` that `_render_module_spec` emitted for empty-condition entries. Switched to checking for "Walking-skeleton boot" (the canonical content) instead, and made the substrate module render skip AC-BOOT-01 from entries (letting `inject_boot_ac` own it). The test caught this immediately.

The `populate_work_items.py` substrate detection is currently string-matching (`ac_ids == ["AC-01"]` → `["AC-BOOT-01"]`). This works but is fragile — a future refactor should carry `is_substrate` through the items tuple rather than inferring it from the default ID.

I'm confident in: the validation gate (substrate with feature ACs → fail, <2 dependents → fail), the boot-probe test generation, the inject_boot_ac idempotency. I'd want eyes on: the `populate_work_items.py` three-path substrate handling (model-driven, yaml, md) — all three copy the same pattern, could be a helper.
