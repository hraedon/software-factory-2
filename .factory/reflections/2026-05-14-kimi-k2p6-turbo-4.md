## On the project

The factory's architecture is solid — the 7-module decomposition (runner, gate, scheduler, router, config, workspace, channel) handles a complex pipeline well. But the opencode integration is a recurring pain point. The channel adapter treats opencode as a simple subprocess, but opencode has opinions about project context, session management, and stdout behavior that leak through the abstraction. BC-141 (empty output from non-project cwd) is the third opencode-specific channel issue after BC-135 (empty output from transient API errors) and BC-044 (family mutation race condition).

The `invocation_cwd` fix is a band-aid. The real solution would be for opencode to support a `--project-dir` flag or for the factory to use opencode's API directly instead of CLI subprocess invocation. But that's a future consideration — the band-aid works.

## On the work done

The debugging was iterative and expensive — 9 attempts at GR-027, each consuming model tokens and time. The first 4 attempts all returned empty output, which I initially misattributed to transient API issues. It took methodical testing (manual shell vs subprocess, different cwds, opencode log inspection) to isolate the cwd dependency. The key insight was checking opencode's own logs at `~/.local/share/opencode/log/` which showed `projectID=global` vs a real project hash.

The BC-143 fix (zombie cycling) was straightforward once I understood the state machine: `release_claim` returns to `new`, which allows re-claiming. The fix (claim → cannot_proceed) is correct but I initially forgot the `.to_dict()` conversion on `ActorMetadata`, causing a second crash. That was a silly mistake — the factory consistently uses `.to_dict()` everywhere, and I should have caught it immediately.

GR-027's 88% lock rate is close to the 90% target. The 4 `cannot_proceed` items (1 test_suite, 1 implementation, 1 review, 1 jury) represent genuine model/reviewer failures that exhausted retries. With `attempt_threshold=4` or a more forgiving inner gate, some of these might lock. The `jury_disagree` exercise is a genuine milestone — K2 and DeepSeek disagreed on a review item, proving the multi-family jury architecture works.
