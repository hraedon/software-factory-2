# Session Reflection — 2026-05-08

**Work summary:** Resolved BC-056 (single-source-of-truth defaults) by creating `factory/constants.py` with 40+ named constants and refactoring all 11 source modules to import from it. Added `worker_actor_id()`, `gate_actor_id`, `scheduler_actor_id` properties to `FactoryConfig` and `family` property to `RoleConfig`. Resolved BC-045 (report.py hardcoded workflow_version) as a side-effect. Also fixed three latent issues spotted during traversal: config `_DEFAULT_WORKSPACE` now derives from workspace constants, gate `ActorMetadata` now derives from `RoleConfig` instead of hardcoded strings, and opened BC-058 for `_STAGE_HANDOFF`/`_PHASE2_DISPATCH` parallel truth against FactoryConfig.

## On the project

The v2 codebase is genuinely well-structured compared to what the breadcrumbs from v1 describe. The separation into runner/gate_process/scheduler/router/workspace is clean, the test coverage is solid (264 tests), and the breadcrumb discipline is mature — every design defect gets a numbered file with frontmatter. That said, the "string constant gravity" pattern that BC-056 identified was real and insidious: I found scattered defaults in 11 files totaling ~80 inline strings, almost all reasonable in isolation but collectively creating a shadow config layer. The constants module fix was mechanical but necessary — without it, Phase 3 multi-channel work would silently diverge.

The pipeline shape (interface_architect → test_author → implementer → gates) is working well enough for sequential single-channel mode. The router's diagnostic-kind-to-role dispatch table is the most fragile piece I touched — it's a flat dict that must be kept in sync with both the gate diagnostic kinds and the config role names. BC-058 captures this properly as a design proposal for Phase 3.

## On the work done

The constants extraction was straightforward but tedious. The trickiest part was `context.py` where an earlier edit accidentally duplicated the `derive_implementer_context` function and lost the `test_suite = p.read_text()` line in the test_suite_ref branch. The test suite caught the syntax error immediately; I had to be more careful with the edit to preserve the original logic.

The `gate_process.py` change to derive `ActorMetadata` from `RoleConfig` is the most meaningful structural fix — it means a config change to the gate channel name will actually propagate, rather than being silently ignored. Before this, `channel="code"` and `family="code"` were constants that would bypass any RoleConfig change.

The config import of `WORK_DIR_NAME`/`WORK_SUBDIR` from `workspace.py` is a minor fix but closes the last duplicate path string. `_DEFAULT_WORKSPACE` is now `Path(WORK_DIR_NAME) / WORK_SUBDIR` — one source of truth.

## Gaps to flag

- `router.py:_PHASE2_DISPATCH` has 18 entries all routing to one of three roles — if a role name changes in config, these won't update. BC-058 tracks this but it's worth noting as the highest-risk remaining parallel-truth.
- `report.py` still has hardcoded shape-category names (`"pure-interface"`, `"error-taxonomy"`, etc.) and state-name comparisons using the constants module — these are read-only display strings, not config, so they're fine.
- `gate.py` still has hardcoded timeouts (30s, 60s, 120s) for subprocess calls. These should probably live in FactoryConfig or at least as module constants, but they're not cross-file duplication so BC-056 doesn't cover them.
- `workspace.py` constants (`WORK_DIR_NAME`, `WORK_SUBDIR`, etc.) are module-level strings rather than in `constants.py`. They're unique to workspace, not shared across modules, so this is acceptable — but if anything else needs to reference `.factory/work`, it should import from `workspace.py`, not hardcode.
- `populate_work_items.py` still has the `"factory-setup"` actor_id and `"interface_spec"` work_item_type as inline strings — these are one-off setup script strings rather than pipeline-hot-path identifiers, but they're technically inconsistent with the constants module.
