**Work summary:** Implemented RFC-027 (test efficacy via mutation testing) end-to-end: wired `mutation_gate.py` into the implementation gate path, added config fields, expanded the mutator operator set from 3 to 6 operators, fixed routing so mutation failures create upstream test_suite revisions (targeting test_author), removed dead code, and updated all tests. 1118 tests pass, 0 lint, 0 dead code.

## On the project

The pipeline architecture is mature and well-structured. The `gate_process.py` → `router.py` → `scheduler.py` flow is clean and extensible. Adding a new gate type (mutation spot-check) required touching 6 files but the changes were mechanical — the architecture welcomed the extension without resistance.

The `Route` dataclass with `create_upstream_revision` / `upstream_type` is a powerful pattern. It lets gates create upstream work items without custom scheduler logic. This was the key insight for the routing fix: mutation failures should create a `test_suite` revision, not loop back to the implementer.

## On the work done

The initial wiring (mutation gate inside `evaluate_implementation`) was correct but incomplete. The Opus adversarial review identified three gaps that were all valid:

1. **Operator set too thin** — The original 3 operators (comparison swap, constant ±1, return-deletion) missed high-yield mutation types. Adding BoolOp swap, not removal, and return-value replacement was straightforward AST work. The `visit_Return` enhancement (True↔False, non-bool→None) was the most involved because it changed the semantics of the existing return-deletion operator.

2. **Routing to wrong role** — This was the most architecturally significant fix. The `MUTATION_UNCAUGHT` route now creates an upstream `test_suite` revision via `create_upstream_revision=True`. The scheduler's `ensure_upstream_revision` already handles this pattern for `REVIEW_FOUND_DEFECT`; reusing it for mutation findings was clean.

3. **Dead mypy branch** — The `GATE_NAME_INNER_MYPY` filter in `evaluate_mutation_spot_check` was unreachable dead code. Removing it and adding a clear docstring was the right cleanup.

The `telemetry.py` changes (harness-attributable deterministic gate rate) were pre-existing uncommitted work from a prior session. They were already in the working tree and passed `make check`, so they ride along in this commit.

## On what remains

1. **Calibration golden run** — The mutation gate is wired but `mutation_gate_enabled` defaults to False. A golden run with `mutation_enabled=True`, `sample_size=12-15`, `fail_threshold=1.0` (observe-only), and fixed seed is the next step. This will produce the first empirical false-accept measurement for cert-watch.

2. **Threshold ratcheting** — After calibration, set per-module thresholds based on the live-rate distribution. Opus suggests blocking at `live_rate > 0.2` on any MVP-scope module.

3. **Prompt enrichment** — The test_author prompt doesn't explicitly render mutation findings. The `review_feedback` context key carries the findings, but the prompt template may need a section for mutation-specific feedback.

## Gaps to flag

- **`telemetry.py` has uncommitted harness-attributable changes** from a prior session that ride along in this commit. These are additive and tested, but the diff is larger than RFC-027 alone warrants. (`src/factory/telemetry.py`)
- **`test_telemetry.py` has a pre-existing `pytest.approx` fix** that was also uncommitted. The import was missing and the assertion was rewritten to use `abs()`. (`tests/test_telemetry.py:906`)
- **The mutation gate runs pre-lock, not post-lock.** Opus's ideal design is a post-lock efficacy gate on the (test_suite, implementation) pair. The current architecture gates work items at `STATE_GATING`; once locked, there's no mechanism to run a gate and route findings to another work item. This is documented in the resolved RFC's calibration note but is a real architectural limitation for future workloads.
