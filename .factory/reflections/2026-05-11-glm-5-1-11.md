## On the project

The factory is in surprisingly good shape for a system this complex with this many moving parts. The architecture is sound: 7-module decomposition (runner, gate, gate_process, router, scheduler, config, workspace) holds up well. The code is consistent in style and conventions. Constants are centralized. The breadcrumb system is working exactly as intended — the adversarial review session produced 20 defects, and every single one had a clear, bounded fix.

What strikes me most is the *density of correctness pressure*. The gate layer, the inner gate loop, the dep resolution, the scheduler — they all have subtle invariants that are easy to get wrong. The fact that 405 tests (now 469) existed before this session and that they still pass after 20 targeted fixes is a credit to the testing discipline. But there's a gap I keep noticing: the golden runs are the *real* integration test, and they're expensive and manual. The unit tests give coverage but not confidence in cross-module behavior.

The venv separation (BC-115) is a good example of something that only matters in practice — gate tooling polluting project dependencies is invisible in unit tests but kills you in golden runs where `requirements.txt` pins conflicting versions.

## On the work done

The good: All 20 fixes were surgical and well-scoped. Each one had a clear before/after. The test additions (credentials, output extraction adversarial, path traversal, reset guard, assertion count) are genuinely testing edge cases, not just exercising happy paths.

The awkward: 

- The scheduler pagination fix (BC-102) required understanding the substrate QueryPage API. I initially wrote defensive `getattr` calls, then checked the actual API and removed them. This is a pattern — the factory depends on substrate's API surface but documents it informally. If substrate changes `has_more` to something else, the scheduler silently stops paginating.

- The circuit breaker (BC-109) is a minimal implementation — counter + exponential backoff. It doesn't reset on success per-channel (it does via `pop`), but it doesn't have a decay mechanism. If a channel fails 3 times, then succeeds, then fails 3 more times, it starts fresh each time. This is fine for Phase 3 but won't scale to fleet mode.

- The ruff-in-tempdir fix (BC-114) is correct but I notice the outer gate's `_run_ruff` now copies the artifact to a tempdir, runs ruff there, and returns a result — but the *content* it checks is the modified content, not the original. This is intentional (we want to know if ruff can make it pass), but the fix means the artifact on disk is no longer mutated. The inner gate was already doing this correctly in tempdir.

- The golden_run_nanny.py is a script, not a Python module. It lives in `scripts/` which didn't exist before. It works but it's bare-bones — no timeout on the overall run, no progress reporting beyond log files.

I'm most confident in: BC-096 (reset guard), BC-097 (redaction), BC-098 (env footgun), BC-101 (JSON extraction), BC-103 (quarantine), BC-111 (path traversal), BC-114 (ruff tempdir), BC-116 (SyntaxError). These are trivial-to-verify fixes with clear test coverage.

I'm least confident in: BC-102 (scheduler pagination) because the substrate cursor API hasn't been exercised in anger with pagination, and BC-109 (circuit breaker) because it hasn't been tested against a real failing channel.

## Gaps to flag

- **`scripts/golden_run_nanny.py`** — the log file handles opened in the process loop are never closed (line 65). Works for a CLI tool but will leak if ever used as a library. Not a bug today.

- **Scheduler pagination (BC-102)** — the fix uses `page.has_more` and `page.cursor` directly from substrate's `QueryPage`. If substrate ever removes or renames these attributes, the scheduler silently stops paginating and falls back to the old O(N) single-page behavior. No test covers multi-page pagination because it requires >100 work items of the same type.

- **Circuit breaker (BC-109)** — `_CHANNEL_BACKOFF_BASE` and `_CHANNEL_BACKOFF_MAX_ATTEMPTS` are module-level constants in `runner.py`. They should be on `FactoryConfig` per the "no inline defaults" convention (BC-056 precedent).

- **`_guard_artifact_size` duplicates `MAX_ARTIFACT_SIZE_BYTES`** — gate.py now has `GATE_MAX_ARTIFACT_SIZE_BYTES` which is the same value as `MAX_ARTIFACT_SIZE_BYTES` in constants.py. These serve different purposes (runner/channel vs gate) but the duplication is a maintenance trap.

- **BC-115 venv isolation** — `ensure_project_venv` no longer installs gate tools into the project venv, but the old `.venv/.deps_hash` file won't detect this change. If a project already has a `.venv` with the gate tools baked in, it won't be cleaned up. The hash only tracks `requirements.txt`, not the gate tools list.

- **`golden_run_nanny.py` cleanup** — the `finally` block has a no-op iteration `for _, log_file_handle in []: pass` that does nothing. Dead code.

- **Pre-gate now runs ruff in tempdir but the outer gate's `_run_ruff` was also fixed** — the gate.py `_run_ruff` function now creates a tempdir, copies the artifact, runs ruff there. This means the ruff result reflects the ruff-fixed version, not the original. This is intentional (we want to know if the code *can be made to* pass lint), but worth noting that the original artifact is never modified anymore, which changes the semantics slightly — previously, if ruff --fix succeeded, the artifact on disk was modified and subsequent inner gates would see the fixed version.
