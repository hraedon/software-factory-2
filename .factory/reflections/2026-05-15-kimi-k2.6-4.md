## On the project

The pipeline is genuinely reaching the limits of its current infrastructure. GR-029 was meant to be the first full cert-watch run through Phase 5 (integration + outcome_verification). It failed not because of the pipeline logic, but because the *scheduler crashed* and the *alternate models disappeared* from the opencode provider registry between yesterday and today. The principal's stated role is architect, not developer — but the system currently demands developer-level debugging (provider health, model availability, transient backend failures) to make forward progress. This is a structural risk: if the golden-run gate requires babysitting model providers, the pipeline can't be trusted for unattended execution.

## On what remains

2. **Model health pre-flight** — `agent_golden_run.py` should smoke-test each configured model with a trivial `opencode run --model <model> --help` before populating work items. This would have caught both dead providers before burning substrate state.
3. **Multi-family jury re-validation** — Both DeepSeek and GLM worked 24h ago. Need to understand if provider IDs changed (e.g. `zai-coding-plan/glm-5.1` vs just `glm-5.1`) or if the providers were removed from the opencode config. Check `~/.config/opencode/opencode.json` for the canonical list.
4. **Outcome verification stage** — Still unexercised in a golden run. The cert-watch full DAG should reach it if the scheduler survives. Consider a smaller fixture (cert-watch-mini) to reduce blast radius for debugging.
5. **Inner gate test_author collect failures** — 2/7 test suites failed `pytest --collect-only` on first attempt. The model may be generating test files with import/module structure that doesn't match the workspace layout. Needs prompt improvement or better import feedback.

## Gaps to flag

- **BC-148** (`breadcrumbs/148-scheduler-crash-golden-run.md`): No known root cause because the scheduler log was auto-cleaned. The `agent_golden_run.py` wrapper has no mechanism to preserve logs on non-successful runs. Consider a `--preserve-logs-on-failure` flag or always keeping logs until the user explicitly deletes them.
- **BC-149** (`breadcrumbs/149-model-availability-regression.md`): Provider death is silent until work items are already created and claimed. A pre-flight model ping would save hours of aborted runs.
- **Jury disagreement cycling with single-family quorum=2**: The same model invoked twice with the same prompt yields different outputs stochastically. This is expected behavior for LLMs, but it means `jury_quorum=2` with a single model is effectively a trap. The config documentation should warn about this, or the runner should auto-detect same-model jurors and warn.
- **Golden run auto-cleanup lost forensics**: The XDG_DATA_HOME isolation worked, but the cleanup ran before I could inspect the isolated DB. For debugging, `agent_golden_run.py` should either (a) keep the isolated DB on non-zero telemetry exit, or (b) copy key files (last N log lines, telemetry summary) to a persistent `.factory/grNNN-forensics/` dir.
- **No error handling in scheduler loop**: Looking at `scheduler.py`, if `_ensure_downstream_item()` or substrate operations raise, the exception likely bubbles to `main()` and exits with code 1. There's no `try/except` around the core loop. This is a known pattern from other modules but the scheduler is particularly vulnerable because it runs continuously for 60+ minutes.
