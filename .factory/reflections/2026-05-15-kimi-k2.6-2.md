## On the project

The factory's architecture is proving genuinely modular. Adding two new work-item types (integration, outcome_verification) and their full mechanical gate stacks required changes in only 7 files (gate.py, gate_process.py, router.py, constants.py, context.py, prompts/integrator.md, workflows/phase5.yaml), and the scheduler didn't need a single new line — its existing pagination-safe handoff loop handled both new types because they're expressed in the config's `stage_topology` as `StageHandoff` objects. That is strong evidence that the "stage topology as data" decision (from the BC-058/060 refactoring sessions) was the right long-term bet.

A tension remains: the substrate link API is still under-exercised. We create links (scheduler creates them on handoffs), but we don't traverse them. The integrator context derivation had to walk a chain through `integration_ref` → jury → review → implementation using only `substrate.get_work_item()` and custom_fields, because `query_links()` doesn't exist in the public API and `create_link`/`remove_link` are the only link methods. This means the context derivation is hard-wiring an implicit DAG shape (integration → jury → review → impl) that may not match future pipeline shapes. It works for now.

## On the work done

### Mechanical gates
The `evaluate_integration()` implementation is now genuinely three gates, not one skeletal gate. Running mypy on an assembled tree of files is straightforward — pass a list of file paths, run mypy --strict. The trickier part was pytest: the integrator prompt asks the model to produce `integration_tests` as a string in the JSON manifest. The gate writes that string to `integration_tests.py` and runs pytest. This means the test file is not a standard pytest discovery path relative to the modules; it just imports the modules by name. That works because the gate runs in a temp directory where all files are flat. A future risk: if `assembled_tree` has nested paths like `src/module.py`, the import statements in integration_tests need to match.

Import resolution was the trickiest gate. The naive `importlib.util` exec_module approach failed when modules imported each other, because Python's import system needs the parent directories in `sys.path`. I fixed this by inserting the temp directory into `sys.path` during the import loop and restoring it afterwards. This correctly handles intra-package imports, including deep paths like `pkg/__init__.py` + `pkg/sub.py`. No sys.path pollution persists after the gate returns.

### Context derivation
`derive_integrator_context()` is no longer a stub. It genuinely walks the integration → jury → review → implementation chain, reads the `artifact_path` from each work item's custom_fields, and injects them into the prompt as `focal_implementation`, `focal_interface`, `focal_test_suite`, plus dependency contents. `derive_outcome_verifier_context()` reads the integration artifact JSON, unpacks `assembled_tree`, and injects every file as `assembled_module_<filename>`. Both handle missing refs gracefully.

### Hidden bug fix
A subtle UUID-lookup bug was caught during testing. `derive_context()` called `substrate.get_work_item(work_item_id)` with a string UUID. In the InMemorySubstrate backend, `_work_items` is a dict keyed by `uuid.UUID` objects. A string key silently returns `None`. Existing code had `_to_uuid()` at the call sites of helper functions but not at the entry point of `derive_context()` itself, so when `derive_integrator_context()` passed the string `work_item_id` directly, the result was a `ValueError: Work item ... not found`. Fixed by adding `_to_uuid()` coercion in `derive_context()` at `context.py:68`.

### Phase 5 YAML
Two bugs in `phase5.yaml` from Session 34 were discovered and fixed:
1. Duplicate link_type names (`derived_from` appeared three times with different source/target pairs). Substrate's `_validate_semantics` rejects duplicate names. Removed the two extra entries — the scheduler doesn't need them for triggering downstream items (it uses `stage_topology`, not link traversal).
2. `integration_ref` was declared on `outcome_verification` but not on `integration`. The integration work item needs a ref field to link back to its upstream jury item for context derivation. Added `integration_ref` to the `integration` custom_fields block.

## On what remains

1. **GR-028** — the first synthetic Phase 5 golden run. Config is written (`golden-run-028-config.yaml`) but not executed. This requires registering `phase5.yaml` with the live substrate fixture (conftest.py still registers `phase1.yaml`). Once that's done, a full 7-stage pipeline run can validate the new gates end-to-end.
2. **Integration gate venv isolation** — the integration gate currently runs mypy and pytest using `sys.executable` (which is the factory's own test venv). For a real multi-module workload, the integration gate should run in a per-DAG venv with assembled dependencies. That's an operational concern, not a code concern.
3. **BC-145 telemetry** — the routing-hint accuracy of `review_found_defect` → upstream revision hasn't been measured in a golden run yet. The mechanism exists but is unvalidated under load.
4. **Link traversal generalization** — the hard-coded chain `integration → jury → review → impl` will break if the pipeline shape changes (e.g., if a future jury ever reviews something other than a review). A small helper to walk links by type ("follow `judges` then `reviews` then `implements`") would generalize this, but needs a substrate API to query links by source_work_item_id. That API may exist internally but isn't exposed publicly yet.

## Gaps to flag

- **`phase5.yaml` link_type deletion may affect link creation.** The deleted duplicate `derived_from` entries were (integration→implementation) and (outcome_verification→integration). The scheduler creates links via `sub.create_link()` in `_ensure_downstream_item()`, but it uses `link_type=handoff.link_type` from `stage_topology`, not from the `link_types` list. For example: the jury→integration handoff has `link_type=derived_from`, so the scheduler creates a `derived_from` link from the integration work item to the jury work item. This is fine even though `derived_from` is only declared once in `link_types` (test_suite→interface_spec), because link creation doesn't validate against `link_types`. If future substrate versions enforce link_type schema validation, we may need to add integration-specific link types back.
- **`derive_integrator_context()` depends on `review_ref` existing on the jury work item.** If the jury is created before the review (shouldn't happen in the scheduler, but if substrate allows it), the chain lookup fails and integrator gets empty extra_artifacts. Silent degradation; the integrator prompt says "If a cross-module import cannot be resolved, set `assembled_tree` to null" — which is correct fallback behavior but not the desired fast path.
- **`golden-run-028-config.yaml` uses `stage_topology` inline in YAML.** FactoryConfig.from_yaml() parses `stage_topology` from lists of dicts into `StageHandoff` objects. This path is tested for config.py unit tests but not for the phase5-specific topology. A malformed YAML (e.g., a list instead of tuple for `additional_links`) would raise at runtime. Low risk but worth validating in a smoke test.
- **Gate budget**: Phase 5 deterministic gates now use 15/16 slots (import, mypy, pytest for integration; plus all pre-existing gates). One slot remains. The first new deterministic gate after this will require spec amendment.
