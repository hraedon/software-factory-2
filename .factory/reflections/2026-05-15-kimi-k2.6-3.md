## On the project

The pipeline is genuinely working end-to-end for Phase 5 stages 1–8 (interface_spec → test_suite → implementation → review → jury → integration). The 92% lock rate on a 3-item DAG with real model calls is credible. What feels fragile is the boundary between the integrator's output shape and the gate's expectations. The integrator produces `assembled_tree` as a flat dict of filenames, but the gate needs a valid Python package tree. We now have mechanical normalization (promote vs remove `__init__.py`), but this is a compensating mechanism for a prompt that doesn't teach the integrator about directory structure. The prompt (`integrator.md`) should probably include a worked example with nested keys like `{"pkg/__init__.py": "...", "pkg/module.py": "..."}`.

The substrate workflow schema requiring unique `link_type` names is a load-bearing constraint we missed in the Phase 5 skeleton. `derived_from` was used three times (test_suite→interface_spec, jury→integration, integration→outcome_verification), which silently broke the scheduler's `create_link` calls. This suggests the Phase 5 skeleton review was incomplete — the `validate_and_build` semantics weren't checked against the intended topology.

## On the work done

**What went well:**
- The agent golden run wrapper (`scripts/agent_golden_run.py`) correctly caught `claim_near_budget` and process crashes. The BC-140 protocol works.
- Telemetry verification passed cleanly (0 orphan submits, 0 unmatched gates, 0 unknown gate names).
- The `routing_hint` instrumentation in `gate.py` + `telemetry.py` is tested and ready; we just need a real failure to measure it.

**What was awkward:**
- The GR-028 first attempt failed because `populate_work_items.py` didn't map `workflow_version=5` to `phase5.yaml`. This is a silly oversight that cost 10 minutes. The version→workflow mapping should be a single source of truth, not an inline dict in populate.
- The integration gate's `importlib` loader needed two separate fixes (dotted module names + flat tree promotion) because the integrator produced inconsistent output shapes across runs. This indicates the gate is too tightly coupled to a specific output convention.
- The scheduler's blind propagation of `dependency_refs` to all downstream items caused `CUSTOM_FIELD_VIOLATION` for `jury`/`integration`/`outcome_verification` types that don't declare the field. The scheduler should have always checked the downstream type's field schema before propagating.

**What I'm not sure about:**
- The `entry_point` promotion logic in the gate (`from .` detection) is heuristic. A malicious or confused integrator could produce an `__init__.py` with `from .` that refers to a module not in the tree. The promotion would create an empty package directory and the import would still fail. We should validate that all relative imports in `__init__.py` resolve to siblings in `assembled_tree` before promoting.
- BC-145 remains open because we never reached `outcome_verification` in GR-028. The routing_hint collection code is tested with mock data, but the real path (integrator → gate → scheduler → runner → outcome_verifier → gate → telemetry) is unvalidated.

## Gaps to flag

- **`src/factory/gate.py:1115-1135`** — Mechanical promotion heuristic (`"from ." in init_text`) is brittle. Could break on comments or strings containing `from .`. Should use `ast` to detect actual relative import statements.
- **`src/factory/scheduler.py:117-125`** — `_downstream_has_field()` is a runtime query to the workflow definition. This is correct but adds a substrate round-trip per handoff. For large DAGs this could be noticeable. Cache the workflow definition in `PipelineRuntime` if profiling shows it matters.
- **`tests/test_gate_process_phase5.py`** — Integration tests use `InMemorySubstrate` with `phase5.yaml`. The live-substrate tests (`TestGateProcessPhase5Integration`) now run against real Postgres, but they don't cover the full handoff chain (integration → outcome_verification). Add a test that creates an `integration` item, gates it, then verifies the scheduler creates `outcome_verification` downstream.
- **`workflows/phase5.yaml`** — The `jury` work_item_type does not declare `integration_ref` as a custom field. The scheduler's `ref_field` for the `jury → integration` handoff is `integration_ref`, but the `jury` type only has `review_ref`. This means the scheduler cannot do ref-field idempotency for this handoff (it will create duplicate integration items if the scheduler restarts). Add `integration_ref` to the `jury` type's custom_fields.
- **`.factory/golden-run-028-log.md`** — Documents that outcome_verification was not reached. This is a known gap, not a failure, but it should be referenced in the next session's worklog entry.
