# Session Reflection — 2026-05-15

**Work summary:** Resolved 15 breadcrumbs (14 factory + 1 substrate-side) across dead code removal, critical bug fixes, scheduler hardening, and test quality improvements. Added `get_workflow(name, version)` to both substrate backends to fix a latent bug where `_downstream_has_field()` called a non-existent API and silently returned False, preventing dependency_refs propagation.

---

## On the project

The breadcrumb backlog is well-maintained — every item was clearly described with root cause, impact, and fix direction. This made batch resolution straightforward. The codebase is clean and consistently structured; conventions are followed rigorously. The main architectural tension remains: the scheduler/runner/gate are independent processes with no coordination mechanism, which surfaces as BC-164 (scheduler idle before handoffs complete) and BC-147 (stuck items on small DAGs). These are real problems but also correctly scoped as "not yet."

The substrate dependency is a genuine coupling point. The `get_workflow` missing API wasn't caught because `_downstream_has_field` has a bare `except Exception: pass` that swallowed the `AttributeError`. That pattern is dangerous — silent failure in a coordination spine is exactly the kind of bug that wastes principal time in golden runs.

## On the work done

Confident in all 15 fixes. The channel backoff deadlock (BC-150) was the most architecturally interesting — the old code permanently disabled channels after 5 failures with no recovery path. The time-based cooldown with probe retry is a pragmatic fix that preserves the backoff intent while allowing recovery.

The scheduler exception handler (BC-161) is a straightforward but load-bearing fix — the scheduler dying silently was the root cause of multiple golden run failures (BC-148). Combined with the monitor now killing remaining processes on crash (BC-167) and preserving logs (BC-162), the golden run observability story is much stronger.

The substrate `get_workflow` addition was the unexpected depth charge. Two tests had been failing silently (`test_dependency_refs_propagated_to_test_suite`, `test_dependency_refs_propagated_to_implementation`) because the scheduler couldn't verify downstream field existence. The fix is minimal — 10 lines in each substrate backend — but the blast radius was "dependency_refs never propagated to downstream work items," which is a correctness bug in any multi-module pipeline.

The BC-153 fix (conditionally-skipped assertions) exposed that the ruff lint test was using auto-fixable code (`import os; import json` — unused imports). The test had *never* been testing what it claimed. The fix uses F821 (undefined name) which ruff cannot auto-fix.

## Gaps to flag

- **`_downstream_has_field` bare except** (`scheduler.py:199`): Even with `get_workflow` now existing, the `except Exception: pass` pattern is still dangerous. If any future substrate change breaks `get_workflow`, the scheduler will silently stop propagating dependency_refs again. Consider at minimum logging the exception.
- **Pre-existing `test_certificate_model.py` collection error**: This test file imports `from interface import ...` which doesn't exist in the test environment. It's been broken for an unknown number of sessions. Not related to this work but should be triaged.
- **BC-154 not addressed**: `_run_ruff_fast` still mutates artifacts in-place. The `.orig` backup is created but the original model output is overwritten. This is a forensic concern more than a correctness one, but it means inner-gate retry chains operate on ruff-modified code, not model output.
- **No tests for the new `get_workflow` substrate method**: Added to both backends without dedicated test coverage. The factory tests exercise it indirectly through `_downstream_has_field`, but a direct substrate test would catch regressions faster.
- **Phase2 dependency propagation was broken in production**: The `_downstream_has_field` failure means all golden runs that used Phase 2+ topology with `dependency_refs` may have had those refs silently dropped. This may explain some GR-level mysteries about cross-module dependency resolution.
