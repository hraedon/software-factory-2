## On the project

The project is in good shape for Phase 2 single-channel validation. The telemetry pipeline is now properly grounded — gate names flow through `actor_metadata` as the primary source, with `payload.diagnostics` as fallback. The string constant discipline from BC-056/065 has been consistently extended to gate names. The substrate `ActorMetadata` schema change was clean and non-breaking (added optional field with defaults).

What feels fragile: `failure_summary.py` had the same bug as `telemetry.py` (reading `gate_name` only from payload, not from `actor_metadata`), and we only caught it because we traced the BC-068 fix across all consumers. There could be other consumers that do the same thing. The `Event` → `custom_fields` confusion (BC-071) is a real footgun — I initially wrote a fallback path accessing `ev.custom_fields` before realizing `Event` has no such attribute.

## On the work done

BC-068 was the anchor fix and it went cleanly. The root cause was two-fold: (1) gate_pass events in `gate_process.py` carried no payload at all, so `telemetry.py` couldn't find `gate_name` in `payload.diagnostics`, and (2) `ActorMetadata` didn't have a `gate_name` field. Adding `gate_name` to `ActorMetadata` and emitting it from `gate_process.py` is the right fix — `actor_metadata` travels with every event, payload doesn't.

BC-069 was mechanical but high-surface-area — 23 constants, touched 8 source files and 6 test files. The ruff import sorting caught one issue. All 299 sf2 + 293 substrate tests pass.

BC-070 was already half-solved by the BC-068 fix to `_gate_md()`. Added a production-realistic test (`test_gate_pass_event_with_no_payload_resolves_from_metadata`) that specifically validates the pass-with-no-payload scenario.

The `failure_summary.py` fix was an opportunistic catch while doing BC-069 — it had the same "read gate_name from payload only" bug. I'm confident in this fix but would flag it for any future audit of event-shape consumers.
