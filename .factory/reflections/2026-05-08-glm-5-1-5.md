## On the project

The project continues to mature. BC-055 was a classic v1 pattern: fallback-to-None everywhere so nothing ever crashes but everything silently degrades. The fix was straightforward once I understood the code, but substrate's validation constraints made testing interesting — work_item_ref fields must be valid UUIDs pointing to existing work items, so I couldn't test the "ref field missing entirely" case through InMemorySubstrate. The defensive `not interface_ref` check stays in the code for robustness, but the realistic failure modes are "ref resolves but artifact_path is empty" and "ref resolves but file doesn't exist on disk."

The router dispatch table is growing. It now has 16 entries in _PHASE2_DISPATCH. The pattern is sound but the table is starting to feel like it wants to be data-driven from the workflow YAML rather than a hardcoded dictionary. That's a BC for another day.

## On the work done

The implementation went smoothly but I hit two issues worth noting:

1. **Substrate validates work_item_ref fields at creation time.** I initially wrote tests that passed empty strings for `interface_ref` and `test_suite_ref`, which substrate correctly rejects. Had to redesign the test strategy to only test realistic failure modes: ref points to a real work item but that item has no artifact_path, or the referenced file doesn't exist. The "field completely missing" case remains coded but untestable through InMemorySubstrate.

2. **Diagnostic kind overwrite bug.** My initial code added `diagnostic_kind` from gate_result to the diagnostics dict unconditionally, which overwrote the router's `cannot_proceed_seam` diagnostic_kind on escalation. Fixed by only adding it when the key doesn't already exist in the router-provided diagnostics. This would have broken the escalation integration test if I hadn't run the full suite.

The `_resolve_ref_artifact()` helper extraction cleaned up gate_process.py nicely — the old code had three copies of the same "look up a ref, get custom_fields, get artifact_path" pattern.

## Gaps to flag

- **Untestable "missing ref" path.** `gate_process.py:111` checks `not interface_ref` but InMemorySubstrate can't create work items without required ref fields. The code path exists for defense-in-depth but has no unit test coverage. Could test with a mock/wrapper that bypasses substrate validation, or accept that substrate-level validation makes this unreachable in practice.
- **`missing_dependency` routes to `cannot_proceed`.** This is the correct behavior per the BC (contract violation can't self-correct), but it means a timing issue where the scheduler creates a downstream item before the upstream artifact lands will immediately escalate to terminal state rather than retry. The `missing_artifact` → `new` path handles the "artifact not ready yet" case. The distinction matters but may need refinement after Golden Run 004.
- **No `diagnostic_kind` on existing gate failures.** The generic diagnostics dict built for non-escalation gate failures doesn't include `diagnostic_kind` when the router provides it. This was already the case before this session; my change only adds it from gate_result when absent. The `diagnostic_kind` field is only reliably present in escalated items (where the router adds it) and in contract-enforcement failures (where my code adds it). Regular gate failures (syntax, stub, etc.) still don't have it in their diagnostics dict. This is a gap but not a regression.
- **`context.py` still has fallback-to-None pattern.** `derive_test_author_context` (context.py:86-96) and `derive_implementer_context` (context.py:111-145) still silently degrade when `interface_ref` or `test_suite_ref` is missing. These are the prompt-building side, not the gate side, so they're less dangerous (a missing context produces a weaker prompt, not a silently-passed gate). Still worth noting as a v1-pattern残留.
