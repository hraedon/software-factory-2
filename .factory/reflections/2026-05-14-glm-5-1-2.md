# Session Reflection — 2026-05-14

**Work summary:** Investigated and resolved BC-135 (glm-5.1 empty output), added empty-output retry + stderr diagnostics to subprocess_channel, validated Gemini CLI adapter end-to-end (fixed Node 24 requirement, added --skip-trust, updated CMD), validated 6 model+provider combinations via opencode, and filed two new breadcrumbs (BC-136: channel failover, BC-137: model capability evaluation).

## On the project

The pipeline is in solid shape. The SubprocessChannel abstraction continues to pay dividends — adding retry and stderr capture was a clean modification to the base class that all three adapters (OpenCode, ClaudeCode, Gemini) inherit. The fact that validating Gemini required only adapter-level changes (CMD flags, nvm PATH injection) and one shared extraction fix (raw JSON fallback) confirms the channel abstraction was the right call.

One thing that struck me: the pipeline has 637 tests but the Gemini adapter had zero integration-level smoke tests. All validation was manual CLI invocations. That's fine for a first pass but the next golden run should exercise Gemini through the pipeline to catch integration issues (workspace trust, Node version, output format edge cases).

The breadcrumb system continues to be the spine of this project. BC-135 went from "proposed" to root-caused to mitigated to resolved in a single session because the breadcrumb captured exactly the right context for investigation.

## On the work done

**BC-135 investigation** went well. The key insight was running `opencode run` with the same prompts that failed during GR-024 and watching them succeed 16/16 times. That ruled out model capability, prompt length, and channel bugs, leaving transient provider issues as the root cause. The timing data from GR-024 logs (10-62s processing time with empty stdout, exit code 0) was the smoking gun — the model was processing but not returning text.

The empty-output retry implementation is clean: config-driven (1 retry, 3s delay by default), transparent to callers, with full stderr diagnostics. I'm confident this is correct. The 13 new tests cover the main paths (retry success, retry exhaustion, bypass on non-empty output, bypass on timeout/error).

**Gemini validation** was more work than expected. The Node 18 vs 24 issue was the first blocker, then the workspace trust error, then the raw JSON extraction gap. Each was a quick fix but it underscores that "validated" means running through the full pipeline, not just the CLI. The nvm PATH injection approach in `_extra_env()` is pragmatic but brittle — if nvm isn't set up on a different host, Gemini silently falls back to system Node 18 and fails. Should document this dependency.

**Model validation** confirmed all 6 model+provider combinations work with the implementer-length prompt (9/9 success across DeepSeek, GLM-5.1 x2, K2 x2). This is good news for BC-136 failover design — there are multiple viable fallback options.

## Gaps to flag

- **`gemini_channel.py:17` — `_NVM_NODE_BIN` is hardcoded to a specific nvm path.** If someone runs this on a different machine or with a different Node version installed via nvm, the PATH injection silently fails and Gemini crashes with the Node 18 error. Should either detect available Node versions or make the path configurable.

- **`output_extraction.py:18-23` — Raw JSON fallback is aggressive.** If a model produces output that starts with `{` but isn't meant to be an artifact (e.g., a prose response starting with a JSON example), it will be captured as the artifact. The `json.loads()` validation prevents garbage but not semantically wrong captures. Low risk since jury/review prompts explicitly ask for JSON.

- **BC-108 is stale.** The resolved breadcrumb says "GeminiCLIChannel disabled — unvalidated." It's now re-enabled and validated. The breadcrumb resolution text is historical so this is fine, but the next agent reading BC-108 might be confused about current state.

- **No integration test for Gemini adapter.** `test_phase3.py` has unit tests for CMD construction but nothing that actually invokes the CLI. Should add a `@pytest.mark.integration` test similar to `test_channel_integration.py`.

- **The `--yolo` flag on Gemini** auto-approves all tool calls. In theory Gemini could write files or execute commands during pipeline runs. This is equivalent to `--dangerously-skip-permissions` on opencode. Worth noting as a security surface for Phase 5+ when specs may come from untrusted sources (RFC-012).
