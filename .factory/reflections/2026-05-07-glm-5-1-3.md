## On the project

The codebase is in good shape. The 7-module decomposition (workspace, channel, context, gate, router, runner, scheduler) from BC-002 continues to hold up well as complexity grows. Each module has a clear responsibility and the interfaces between them are narrow. Adding the subprocess gates and escalation routing was a straightforward extension, not a refactor.

The Phase 2 plan is well-structured. Each wave has clear exit criteria and the wave ordering prevents building on shaky foundations. Waves 0–5 are now done; Waves 6–8 remain. The plan's estimate of 10–14 days looks roughly right — Waves 0–5 took about 3 sessions.

One thing that concerns me: the scheduler is the weakest module and it knows it. It uses polling, it does O(n) idempotency checks via custom_fields matching, and its `_ref_field_for` helper is a hardcoded dispatch table. This is all acknowledged in the plan and acceptable for Phase 2, but it'll need a proper substrate hooks integration before Phase 3 adds parallelism.

## On the work done

The subprocess gates in `gate.py` are the biggest piece of new code. They're straightforward — each runs a subprocess, captures output, maps to the right DiagnosticKind. The `shutil.which` guard means they degrade gracefully when a tool isn't installed (mypy isn't on this system). I'm confident in the pytest and ruff gates since both tools are available and I tested them. The mypy gate is untested against a real mypy run — it will fire during golden-run-002 when the system has mypy installed.

The scheduler idempotency fix is correct but not elegant. Querying all downstream items and checking custom_fields refs in Python is O(n). The right fix is a substrate `query_links(to_work_item_id=X, link_type=Y)` API. I noted this but didn't build it.

The escalation routing is clean. The `_ESCALATABLE_KINDS` set and threshold check in `route()` are easy to understand and test. The `gate_process.py` change is minimal — just passes two extra parameters. The router's backward compatibility is maintained via default parameter values.

The substrate `read_events` fix was unexpected. The working copy had reverted BC-039's composable filter implementation back to mutually-exclusive if/elif branches. I re-applied the fix with correct sort order (oldest-first for work_item_id queries, newest-first for global queries). This needs committing in substrate.

## Gaps to flag

- **Substrate `read_events` regression not committed** (`/projects/substrate/src/substrate/_in_memory.py:539-565`). The composable filter fix is in the working tree but uncommitted. If someone does `git checkout` on substrate, this regression will resurface and `test_channel_failures.py` will break.

- **No `query_links` API in substrate**. The scheduler's O(n) idempotency check is a workaround for the absence of a reverse-link query. Not blocking for Phase 2 but will be a performance issue in Phase 3 with parallel workers.

- **mypy gate is untested against real mypy** (`gate.py:_run_mypy`). The gate skips silently when mypy isn't installed. During golden-run-002, verify mypy is on PATH and the gate actually fires.

- **`_is_forbidden_impl_import` is conservative** (`gate.py:335-336`). Only blocks `conftest` and `pytest`. An implementation could import `unittest`, `sys`, or other modules that shouldn't appear in production code. The Phase 2 plan's gate spec calls for import validation against the locked interface — the current check is a weaker approximation.

- **`evaluate_implementation` gate ordering hardcodes pytest before ruff** (`gate.py:305-314`). This means a lint issue won't surface if tests fail first. Probably correct (tests are more important) but worth noting — a worker gets one diagnostic per gate cycle, and the cycle cost is a full re-invocation.
