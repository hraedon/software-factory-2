# Session Reflection — 2026-05-11

**Work summary:** Implemented Phase 3 fleet integration infrastructure (multi-channel dispatch, Gemini adapter, credentials) and resolved three open breadcrumbs (BC-085, BC-086, BC-058). The session spanned two distinct work streams: the Phase 3 foundation (8 files new/modified, 22 tests) and the inner gate + config refactor (6 breadcrumbs-relevant files, 17 more tests). 422 tests pass, 0 lint/audit errors.

## On the project

The architecture is maturing well. The `SubprocessChannel` base class made adding new channel adapters trivial (Gemini was ~25 lines). The Phase 3 config pattern (`FactoryConfig.phase3()`) is clean and the per-role channel selection via `channel_for_role()` on `PipelineRuntime` is the right abstraction — it's backward compatible (single-channel still works via the `channel` fallback) and doesn't over-engineer for Phase 4's jury/race patterns.

The inner gate extension (BC-085/086) is the highest-leverage change in this session. The `_inner_gate_loop` was already well-factored; generalizing it to all three roles was mechanical. The `_run_pre_gate` dispatch is simple and correct. I'm confident this will recover a meaningful portion of the GR-014 tail.

BC-058 was necessary hygiene. The `_STAGE_HANDOFF` dict was a latent coordination hazard — having role names in three places (config, scheduler, router) would have bitten hard when adding cross-family reviewer or frontier judge roles. The `StageHandoff` dataclass and `stage_topology` on `FactoryConfig` is the right single-source-of-truth pattern. One concern: the `additional_links` tuple on `StageHandoff` is a bit of an escape hatch — if the pipeline gets more complex handoffs with conditional link creation, this dataclass may need to grow. But for Phase 3's three-role chain it's fine.

## On the work done

The Phase 3 work went smoothly. The multi-channel dispatch change to the runner was the most delicate part — the `worker_loop` previously used a single `channel` variable throughout, and replacing it with per-role lookup required touching the claim transition and the `process_work_item` function. The `channel_for_role` method on `PipelineRuntime` is a clean solution that keeps the change localized.

The credential infrastructure (`credentials.py`) is minimal and correct. The `inject_credentials_into_env` function is the right pattern — per-provider env var injection without leaking into the global environment. The redaction helper is defensive. One thing I didn't do: wire credential loading into the actual channel invocation env for real providers. The `_resolve_extra_env` helper in runner.py loads credentials but since opencode handles its own auth, the credential injection won't be exercised until we have a channel that needs explicit API key injection (likely when K2 gets a direct API adapter rather than going through opencode).

The pre-gate refactor was clean. `_run_import_check` and `_run_collect_only` follow the same pattern as the existing `_run_mypy_fast` and `_run_pytest_fast`. The `TEMPFILE_PREFIX_COLLECT` constant was already in constants.py but unused — good, now it has a purpose.

The BC-058 refactor cascaded into more test changes than expected (4 test files needed `FactoryConfig.phase2()` instead of bare `FactoryConfig()`). This is actually a sign the refactor was needed — those tests were implicitly depending on Phase 2 scheduler behavior while using Phase 1 config. The fix makes the test intent match the config.

The config binds interface_architect→Claude, test_author→K2 (Fireworks), implementer→GLM (z.ai). This is the first time different channels will be used for different roles in the same run.

**Pre-existing substrate regression:** `check_role_gating` NameError in `substrate/_in_memory.py:500`. This causes 58 test failures on the base commit (before any of my changes). The tests that fail all involve transitions with `actor_metadata` containing a `role` field against a workflow with `allowed_roles` restrictions. This is a substrate bug, not a factory bug — but it means `make check` on the base commit also fails. The 422 tests that pass are the ones that don't exercise that code path. This should be reported to the substrate maintainer.

## Gaps to flag

- **Gemini adapter untested in real invocation.** `gemini-cli` v0.41.2 has a Node.js v18 incompatibility on this host (needs v20+). The adapter code is correct but can't be validated until the Node version is updated or the CLI is run on a different host.
- **Credential injection not end-to-end tested.** The `_resolve_extra_env` function loads credentials but the opencode channel handles its own auth. No integration test verifies that a provider key actually gets injected into a subprocess environment during a real invocation.
- **`_ref_field_for` still uses hardcoded type strings.** `scheduler.py:162` has `if next_type == WORK_ITEM_TYPE_TEST_SUITE` — this could be derived from the workflow YAML's custom_fields schema. Not urgent for Phase 3's three types but will become a coordination hazard if new work-item types are added.
- **Inner gate for interface_spec doesn't check dependencies.** BC-085's out-of-scope section explicitly excludes cross-module import checks. This is correct for now (interface_spec stage doesn't have locked deps yet) but will need revisiting if the pipeline adds a "resolve dependencies before interface_spec" stage.
- **`_PHASE2_DISPATCH` in router.py still has hardcoded routing.** BC-058 addressed the scheduler's parallel truth but the router's diagnostic dispatch table remains a module-level dict. The breadcrumb mentioned both; I only fixed the scheduler side. The router side is lower priority since it doesn't duplicate role names (just maps diagnostic kinds to states), but it's worth noting.
