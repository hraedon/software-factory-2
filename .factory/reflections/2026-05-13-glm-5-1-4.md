# Session Reflection — 2026-05-13

**Work summary:** Resolved two breadcrumbs (BC-133: telemetry two-source-of-truth, BC-134: jury observability gap), built a broken-impl fixture and ran three golden runs (GR-023/024/025), implemented multi-model jury support via `model_override` on the Channel protocol, and promoted glm-5.1 through isolated role validation and mixed-family jury exercise.

## On the project

This project is in remarkably good shape for its complexity. The seven-module decomposition holds up well — changes to jury.py, gate.py, runner.py, telemetry.py, and event_schemas.py all landed cleanly with zero test regressions. The Phase 4 architecture (review + jury) was clearly designed to be extensible, and adding `model_override` to the Channel protocol was a one-line addition to the Protocol with a natural implementation in SubprocessChannel. The breadcrumb discipline is excellent — every defect has a home, and the resolved breadcrumbs form a genuine audit trail.

The one thing that feels fragile is the `_resolve_jury_channels()` keying scheme. Using `f"{rc.channel}-{model_id}"` to generate unique juror keys works but is ad-hoc. If two RoleConfig entries share the same channel AND model (e.g., for A/B racing), the keys collide silently. This is fine for Phase 4 but will need a proper juror identifier for Phase 5 fleet scenarios.

The telemetry two-source-of-truth fix is clean — `SubmitPayload.inner_gate_attempts` is the right place for this data. But I note that the exit criteria metrics struct now has 16 fields. At some point it should probably be decomposed into outer-gate metrics and inner-gate metrics sub-structs.

## On the work done

BC-133 (inner-gate telemetry) was the most invasive change: touched event_schemas.py, runner.py, telemetry.py, and tests. The key insight was that custom_fields on WorkItem are a footgun (BC-071 precedent), so using the submit event payload was the correct approach. The `_inner_gate_loop()` return type changed from 3-tuple to 4-tuple, which cascaded through all return paths. I'm confident this is correct because all four return paths now explicitly include the `inner_gate_attempts` list.

BC-134 (jury observability) was straightforward — the fix was to always populate `disagreement_rationale` when quorum is not met, with a `[all_against]` tag for the all-against case. The gate.py change to detect the tag and produce different diagnostics is clean.

The multi-model jury support (for GR-025) required adding `model_override` to the Channel Protocol and SubprocessChannel. This is a minimal, backward-compatible change. The family derivation fix (using `model_override` for family when provided) was caught during GR-025 review — without it, both jurors showed `family: "fireworks"` because `_derive_invocation_family()` read the first RoleConfig's model.

The broken-impl fixture (GR-023) produced correct code — K2 nailed the 3-AC spec on first attempt. The fixture itself is useful as a quick smoke test for Phase 4.

GR-024 (glm-5.1 isolated) showed that glm-5.1 can handle interface_architect and test_author roles but consistently fails for implementer with empty output. GR-025 (mixed-family jury) validated the multi-model infrastructure but glm-5.1's empty output prevented quorum=2 from being met. These are model reliability issues, not pipeline bugs.

## On what remains

1. **BC-135 (glm-5.1 empty output)** — Needs investigation: is it prompt length, output format, or rate limiting? A truncated-context retry strategy would help. This blocks reliable multi-family jury with glm-5.1.

2. **BC-120 (implementer-initiated interface amendment)** — Still deferred. The jury disagreement → back-to-interface_architect path would be the natural trigger, but it's not wired yet.

3. **Phase 5 planning** — All Phase 4 validation steps are now done. The project is ready for Phase 5 planning: integration, outcome verification, first real workload.

4. **Family derivation for model_override** — The fix I applied uses `FAMILY_BY_PROVIDER` directly in `subprocess_channel.py` rather than going through `_derive_invocation_family()`. This works but duplicates the family-derivation logic. A cleaner approach would be to have `_derive_invocation_family` accept an explicit model parameter.

## Gaps to flag

- **`_resolve_jury_channels()` key collision** (`runner.py:768`): Two RoleConfig entries with same channel+model produce identical keys. Silent data loss in the dict. Fine for current use, but needs explicit handling for A/B racing.

- **`custom_fields_update` in event payloads**: Telemetry logs `event_schema_unknown_fields: class=SubmitPayload fields=['custom_fields_update']`. The substrate is writing extra fields to event payloads that SubmitPayload.from_dict() doesn't expect. The warning is harmless but noisy. Consider adding to the known-fields set or having substrate stop writing it.

- **Exit criteria report still checks "Phase 3" targets**: The report label says "Pipeline" now, but the target thresholds (>=60% first-pass, >=90% lock rate, <=2.0 mean attempts) are still Phase 3 exit criteria. Phase 4+ may need different thresholds (e.g., including jury pass rate).

- **No `make check` gate in CI**: The README mentions `make check` but there's no CI pipeline configured. All validation is manual (golden runs + `make check` locally). A pre-push hook or GitHub Actions workflow would catch regressions earlier.

- **Golden run config sprawl**: There are now 5 golden-run config files (GR-021 through GR-025) in the repo root. These should probably live in a `golden-runs/` or `configs/` directory to keep the root clean.
