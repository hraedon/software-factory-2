# Session Reflection — 2026-05-29

**Work summary:** Implemented RFC-038 conformance gate MVP — a deterministic, execution-based gate that replaces LLM-opinion-based outcome_e2e for AC conformance verification. Built AC-to-pytest translator, wired gate into pipeline dispatch/router/telemetry, validated against GR-048 artifacts (all 4 fail deterministically). 31 new tests, 1149 total passing.

---

## On the project

The codebase is well-organized. The gate infrastructure (evaluate_* functions returning GateResult, KIND_DISPATCH routing, ESCALATABLE_KINDS) is clean and extensible — adding a new gate type was straightforward. The spec's phase budget enforcement (test_gate_budget.py) is a good guardrail that caught the addition immediately.

The v1 precedent chain (dep-v1-314, dep-v1-342, dep-v1-364) is unusually well-documented. The RFCs reference specific prior failures with concrete evidence, not vague "we tried this before" hand-waving. That makes the design decisions load-bearing rather than opinion-based.

## On the work done

The AC translator is the weakest part. It works for url-shortener's scenario format ("Given a POST to /links with {...}, the response is HTTP 422") but the regex-based parsing is brittle. The `_parse_scenario` function handles the patterns in the current fixtures but will break on scenarios with different phrasing. The RFC correctly identifies this as "the load-bearing risk" — deterministic templating is the right default, but the templating itself needs hardening before it generalizes.

The gate_process dispatch is slightly awkward: it resolves the integration artifact from `integration_ref` on the outcome_verification work item, checks for non-empty assembled_tree, then falls back to LLM verdict. This works but the fallback path means the conformance gate silently doesn't run in degenerate cases (empty tree, missing spec_section). That's correct for backward compatibility but makes it hard to know whether conformance was actually tested in a given run. Telemetry should track this.

The GR-049 validation (pointing at existing GR-048 output) confirmed the diagnosis: all 4 integration artifacts fail deterministically. The first one (efd0a3b8) cleanly shows "No FastAPI app — cannot test HTTP behavior" via pytest.fail(). The others have ImportErrors from `interface.py` — these are the stub artifacts with no HTTP layer.

## On what remains

1. **GR-049 proper** — Run a full golden run with the conformance gate wired in. Needs a config that propagates `spec_section` to outcome_verification. This is the real validation — running against the existing artifacts only proves the gate catches stubs, not that the pipeline uses it correctly.

2. **AC translator generalization** — The current translator only handles url-shortener's scenario format. Need to test against log-redact-cli and dep-graph-viewer ACs. The `_parse_scenario` function will likely need new patterns (file operations, DOT output assertions, count assertions).

3. **RFC-039 validation** — Deliverable-decomposed url-shortener through the same gate. This tests whether vertical slices can own and pass their ACs where atomic units could not.

4. **Upstream revision routing** — The conformance gate routes to `STATE_NEW` on failure but doesn't create upstream revisions. The RFC suggests routing failures to the responsible upstream work item with the concrete failing scenario. This needs a new DiagnosticKind handler in the router.

5. **BC-226** — Spec-lint AC concreteness check. Filed as a breadcrumb but not implemented. This is the preventive counterpart — catches degraded ACs at spec-authoring time.

## Gaps to flag

- `src/factory/gate/conformance.py:_parse_scenario` — regex-based scenario parsing is brittle. Will break on scenarios that don't match "Given a POST to /links" or "POST /links {body}" patterns. Needs a proper scenario parser or a different translation approach.
- `src/factory/gate_process.py:435-468` — conformance gate silently falls back to LLM verdict when assembled_tree is empty or spec_section is missing. No telemetry signal for whether conformance was actually tested. Should log when falling back.
- `src/factory/gate/conformance.py:_derive_acceptance_tests` — the `has_fastapi` detection is naive (checks if "fastapi" appears in requirements or filenames). A spec that declares FastAPI but the artifact doesn't import it would still generate tests that expect a FastAPI app.
- `tests/test_gate_conformance.py` — no integration test that actually runs a working FastAPI app through the conformance gate. All tests use stub artifacts. A "happy path" test with a real FastAPI app would catch regressions in the test generation.
