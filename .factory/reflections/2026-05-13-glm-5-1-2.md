# Session Reflection — 2026-05-13

**Work summary:** Implemented BC-131 (runtime import resolution feedback), ran GR-021 to validate it (100% lock rate, 74% inner gate first-attempt rate, 5/5 wrong_module_name recoveries), then implemented fleet triage (disabled Gemini channel, switched implementer to K2-only) and fixed the deterministic gate classifier in telemetry.

---

## On the project

The project is in strong shape for Phase 3 exit. GR-021 demonstrated 100% lock rate and 74% first-attempt inner gate pass rate. The BC-131 fix (structured import failure feedback) had an immediate, measurable impact: every interface_spec that hit `wrong_module_name` in the inner gate recovered on retry=1 after receiving the new feedback. The pipeline is mechanically reliable.

One structural concern: the inner gate loop doesn't emit Substrate transition events. This is architecturally correct (the inner gate is pre-submission, not a state machine transition), but it means the telemetry module can't compute inner gate first-attempt rates from Substrate data alone. I started down the path of adding `gate_pass`/`gate_fail` transitions but hit a Substrate constraint (`gate_pass` not valid from `in_progress`). The right fix is either (a) a custom metadata-only event in Substrate, or (b) a log-based telemetry aggregator. For now the data lives in structlog and manual analysis, which is fine for Phase 3.

## On the work done

BC-131 implementation went smoothly. The `_parse_import_failure` function is clean and well-tested (14 test cases). The `import_feedback` field flows through `PreGateResult` → `PromptContext` → `render_prompt` → model retry prompt, which is the correct architecture: the pipeline teaches the model its own constraints rather than silently failing.

One bug: I initially used `min()` instead of `max()` for the Levenshtein suggestion, so "Did you mean?" was suggesting the *least* similar module name. Caught by the test suite immediately. Good reminder that `min()` vs `max()` with a key function is a common footgun.

Fleet triage was straightforward — removed `GeminiCLIChannel` from runner registration, changed the implementer default model from `glm-5.1` to `kimi-k2p6-turbo`. The test that asserted `"zai" in implementer.model` needed updating.

The telemetry deterministic gate fix: added composite gate names (`interface_spec`, `test_suite`, `implementation`) to the deterministic set. These are mechanically deterministic outer gates. The `test_suite_assertions` sub-gate was already correctly classified; the real issue was that the outer composite gate names weren't in the set.

## Gaps to flag

- `runner.py:517-535` — inner gate `passed`/`failed_retry` events are structlog-only, not Substrate events. This is correct but means `telemetry.py` can't see inner gate outcomes. Future telemetry work should address this.
- `tests/test_import_feedback.py` — the `test_dotted_import_includes_feedback` test through `pre_gate_interface_spec` depends on ruff not stripping unused imports. If ruff changes its unused-import behavior, this test may become flaky. The direct `_run_import_check` tests are robust.
- `src/factory/pre_gate.py:468-470` — the `_parse_import_failure` function uses `re` and `difflib` which are stdlib, but the regex patterns are fragile across Python error message format changes. Consider adding version guards if Python 3.14+ changes ModuleNotFoundError formatting.
