## On the project

The project is in a healthy state. 469 tests pass, 0 lint errors, and the open breadcrumb count has been steadily shrinking. The architecture is coherent: substrate as an append-only provenance spine, factory as a deterministic pipeline that converts specs into tested code.

The Gemini review was technically literate but consistently overstated severity by treating a single-user development tool as a multi-tenant SaaS product. The one genuinely useful insight — credential stripping in gate subprocesses — was buried under breathless "reverse shell" language that ignored the actual operating model (the LLM already has shell access via the channel adapter).

The most valuable external feedback was the architectural critique of interface-first rigidity and the "context diet" idea for failure summarization. ## On the work done

Three breadcrumbs resolved with code:
- BC-078 (benchmark scope): Pure housekeeping — all proposed fixes were already done by prior sessions. Just moved to resolved.
- BC-118 (nanny timeout/progress): Straightforward addition of `--timeout` and periodic status output to golden_run_nanny.py. Clean implementation.
- BC-119 (gate hash versions): Changed `_gate_tools_hash()` to query `pip show` for installed versions. This works but has a subtle property: the hash is now computed *after* installation and *after* a potential venv rebuild. If the gate venv already exists with stale tools, the first check computes the hash from the existing (stale) versions, which will differ from the stored hash only if someone manually upgraded a tool. This is the intended behavior but worth noting.

RFC-013 implementation was the substantial piece. The changes are well-contained:
- `pre_gate.py`: Added `_fail()`/`_ok()` helpers that standardized the return dict shape across all 5 `_run_*` functions. This actually cleaned up the code — the inline dict construction was getting repetitive. `PreGateResult.output` carries raw tool output (truncated to 5KB at source, further truncated by config at consumption).
- `runner.py`: Minimal change — just passes `pre_result.output` through to `FailureEntry.gate_output` with config-controlled truncation.
- `context.py`: `render_prompt` emits gate output in a code block. The indentation pattern (`  {line}`) is simple but might interact oddly with very long lines in the output. The config default of 2000 chars should keep this manageable.
- `failure_summary.py`: Just added the field. No behavior change for existing code paths (gate_fail/channel_fail events from substrate don't carry gate_output).

I'm confident in all changes. The RFC-013 implementation follows the existing patterns closely.

## Gaps to flag

- `pre_gate.py:_truncate_raw_output` keeps the *tail* of the output. For mypy, the most useful errors are at the top (the summary). For pytest, the most useful output is at the bottom (the traceback). The tail-keeping may not always be optimal. Consider per-tool truncation strategy in a future iteration.
- `venv.py:_installed_versions_string` runs `pip show` for each gate tool, which means 3 subprocess calls. This runs every time `_ensure_gate_venv` checks an existing venv. The overhead is small (~1s) but worth noting for hot-path optimization.
- BC-120 (interface amendment) was filed based on external review feedback, not on observed golden-run failures. GR-014's 2 escalations were model quality issues, not contract issues. The breadcrumb may sit dormant until the factory processes specs where the interface is genuinely wrong. This is fine — it's a Phase 4 item.
- The RFC-014 staff engineer summarizer depends on a cheap model being available for the summarization call. The current config doesn't have a "summarizer model" concept. This will need a config field when implemented.
- AGENTS.md says "0 critical" but the breadcrumb count is now 5 open (0 critical, 2 high, 3 medium, 0 low) + 14 RFCs. Verify the count is accurate after this commit.
