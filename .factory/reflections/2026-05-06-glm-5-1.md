## On the project

The project is in genuinely good shape for its phase. Opus's architectural groundwork is meticulous — the spec (300 lines), the plan (236 lines), the workflow YAMLs, and the breadcrumb chain (BC-001 through BC-003) are all internally consistent and reference each other correctly. This is rare. Most specs I've worked with have drifted from their implementation by this point; this one hasn't because there was barely any implementation until Kimi's session.

The runner skeleton is structurally sound. The 7-module decomposition (workspace, channel, context, gate, router, runner, failure_summary) maps cleanly to the spec's concerns, and each module is small enough to reason about independently. The workspace module in particular is well-designed — the manifest/sha256/quarantine approach gives real forensic value without overcomplicating the happy path.

The biggest structural concern is that `process_work_item` is doing too much in one function — claim → resume check → context derivation → channel invoke → manifest write → substrate transition. It works at ~80 lines but will be hard to extend in Phase 2 when roles multiply. A decomposition into smaller functions (one per phase of the claim lifecycle) would make the retry/failure paths easier to test individually.

## Gaps to flag

- `runner.py:85-90` — The worker loop still does a separate `sub.transition("claim", ...)` after `acquire_claim`. This is correct for substrate (claim acquires the lock, transition records the event), but it means a crash between `acquire_claim` and the `claim` transition leaves the item in a state where the claim is held but no event records it. The idempotency code handles the artifact side but not this event-gap side. Worth a breadcrumb for Phase 2.

- `runner.py:113` — `wr = Path(config.workspace_root)` changed from `work_root(Path(config.workspace_root))` during Kimi's edits. The `work_root()` function prepends `.factory/work/`. If `workspace_root` is already set to `.factory/work`, this is fine. If it's set to just `.factory` or the project root, artifact paths will be wrong. Verify which convention is canonical.

- `test_pipeline_mock.py` — The MockSubstrate tests don't exercise the `gating` state's `claimed_by` semantics. The real substrate gate loop checks `claimable_now=True`, which excludes items already claimed. The mock's `query_work_items` simulates this by checking `claimed_by`, but the acquire-then-query sequence in tests doesn't fully exercise the race condition where two actors try to claim the same item.

- `gate_process.py:99-104` — The gate process hardcodes `role="mechanical_gate"` and `channel="code"` in actor metadata. This is correct for Phase 1 but will need to be configurable for Phase 2 when multiple gate roles exist.

- `workflows/README.md` — The "Hook-driven stage progression" open design question (#5) is still open. This is the mechanism by which `gate_pass` on an `interface_spec` creates a `test_suite` work-item. Without it, Phase 2's multi-role pipeline has no automated stage progression — the runner would need to be the orchestrator. This is a significant design gap that should be a breadcrumb before Phase 2 starts.
